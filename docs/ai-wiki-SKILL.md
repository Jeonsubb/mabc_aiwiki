## 0. 문제정의와 실용성

- **누가/언제**: AI 대화를 자주 하는 일반 사용자, 클로드를 업무·취미·학습·아이디어 정리 등에 쓰는 사람.
- **반복 빈도**: 대화는 매일/매주 발생하지만, 나눈 내용이 위키처럼 누적되지 않아 나중에 다시 찾으려면 채팅 기록을 처음부터 훑어야 하는 일이 반복된다.
- **소요 시간**: 대화 내용을 다시 찾거나 그 때 나눈 아이디어를 다시 정리하는 데 매번 시간이 들고, 비슷한 주제를 다시 처음부터 이야기하는 경우도 생긴다. 대략 대화 1건당 다시 찾는 데 몇 분, 비슷한 주제 재탐색 시 다시 정리하는 데 더 큰 시간이 생길 수 있다.
- **현재 방식 한계**: 채팅 기록은 남아도 주제·관심사가 섞인 채 쌓여서 재사용 가능한 지식으로 이어지지 않는다. 요약만 하면 사라지고, 연결·갱신·추적이 안 남는다.
- **이 스킬로 줄어드는 것**: 다시 찾는 시간, 다시 묻는 시간, 관심사/아이디어가 사라지는 손실, 흩어진 대화를 주제별로 다시 모으는 수고.

# AI 대화 주제별 위키 정리 스킬 (ai-wiki)

## 1. 역할

사용자의 AI 대화·메모·아이디어·링크·떠오른 생각을 **주제별 위키**로 정리해, 다시 찾고 이어 쓸 수 있게 만드는 정리자.

단순 요약이 아니라, **쌓이고 연결되고 갱신되는 위키**를 목표로 한다.
입력마다 다음을 함께 다룬다.

- 주제/프로젝트/관심사 후보를 뽑는다
- 기존 위키 구조가 있으면 들어갈 위치를 먼저 찾는다
- 새 항목이 필요하면 초안(제목·한 줄 요약·핵심·관련 아이디어/링크·연결 후보)을 만든다
- 유사·중복 가능성이 있으면 병합을 강제하지 않고 표시한다
- 태그가 없어도 "분류 대기"로 버리지 않고 후보 분류를 붙인다
- 개인정보/민감 내용은 노출하지 않고 경고만 남긴다
- **새로 생긴 관심사 / 계속 파볼 것**을 따로 목록화한다

## 2. 입력

- AI 대화 텍스트, 복붙 메모, 내보내기 텍스트, 아이디어 조각
- 선택적 태그/프로젝트명/관심 카테고리 (없어도 처리)
- 기존 위키 구조가 있으면 그 구조 (없으면 새로 제안)

## 3. 호출 방식 — 사용자용 프롬프트 세트

아래 세 프롬프트는 사용자가 이 스킬을 부를 때 그대로 복사해 쓸 수 있는 호출 문장이다.
어떤 형태로 불리든 같은 절차로 처리한다.

### 기본형 (가볍게 시작)
> "내가 AI랑 나눴던 대화/메모/아이디어를 주제별 위키로 정리해줘.
> 지금은 태그가 없어도 괜찮고, 네가 주제 후보를 몇 개 잡아서 제안해줘.
> 정리 결과물은 각 주제별 디렉터리 아래에 항목으로 남기고,
> 새로 생긴 관심사나 계속 파볼 만한 것도 따로 표시해줘.
> 민감해 보이는 개인정보는 별도로 표시만 하고 그대로 노출하지 말아줘."

### 구체형 (의견을 더 얹고 싶을 때)
> "다음 AI 대화 내용을 주제별 위키로 정리해줘.
> - 주제 후보 3개 정도를 먼저 제안하고, 내가 고르거나 조정할 수 있게 해줘
> - 각 항목은 제목, 한 줄 요약, 핵심 내용, 관련 아이디어/링크, 연결된 기존 항목 후보 형식으로 남겨줘
> - 비슷한 내용이 이미 있으면 무조건 병합하지 말고, 유사 항목 표시하고 병합/분리 선택권을 줘
> - 태그가 전혀 없는 내용이면 '분류 대기'로 두지 말고 후보 분류를 붙여줘
> - 개인정보/민감해 보이는 내용은 저장 범위를 경고 표시하고, 그대로 퍼뜨리지 말아줘."

### 이미 조금 쌓인 위키에 추가형
> "기존 위키 디렉터리 구조가 이미 있어.
> 새로 들어온 AI 대화/메모를 이 구조에 맞춰서 넣어줘.
> - 어디에 넣을지 먼저 알려주고
> - 새 주제가 필요하면 새 디렉터리/항목 후보와 이유를 제시해줘
> - 기존 항목과 중복 같으면 병합할지 분리할지 의견을 같이 줘
> - 이번 내용에서 '계속 추적해볼 만한 관심사'가 보이면 따로 표시해줘."

## 4. 운영 규칙 (핵심)

이 스킬은 사용자의 AI 대화·메모를 **MCP 위키 제안(add/change)**으로 정리할 때 쓴다.
결과물을 직접 wiki/에 쓰지 않고, MCP 도구로 pending 제안까지만 저장한다.

### 4-1. 사용자 발언과 AI 제안 구분

- 사용자 발언(원문)과 AI 제안(정리본 초안)을 섞지 않는다.
- 위키 본문에는 사용자 발언에 있는 내용만 근거로 넣고, 원문에 없는 사실·전망을 임의로 추가하지 않는다.
- AI가 덧붙이는 해석·전망은 반드시 "추론" 또는 "가능성"으로 표시한다.
- 시나리오·예측은 확정적 사실처럼 쓰지 않는다.

### 4-2. 내용 작성 원칙

- 원문에 있는 내용만 근거로 쓴다.
- 원문 근거가 없는 내용은 넣지 않는다. 꼭 넣어야 하면 추론이라고 명시한다.
- 한글 문서에 불필요한 영어나 한자를 섞지 않는다.
- 같은 내용을 두 번 정리하지 않도록, 먼저 기존 위키(제안/노드)가 있는지 확인한다.

### 4-3. MCP 제안 저장 흐름

- 대화 원본은 MCP 도구 submit_conversation으로 먼저 저장한다.
- 제안은 MCP 도구 create_proposal로 만들며, pending 상태로만 저장한다.
- content에는 title, summary, body, tags, related만 사용한다.
- rationale은 content가 아닌 별도 인자로만 전달한다.
- target_node_id는 content에 넣지 않고 별도 인자로만 전달한다.
- change 제안을 만들 때는 실제 대상 위키 node_id가 있어야 하며, 없는 ID로는 생성하지 않는다.
- 승인·기각·위키 직접 변경은 MCP 도구로 하지 않는다. (별도 승인 경로 사용)
- content에 허용되지 않은 키(예: rationale, status, target_node_id)가 들어가면 생성 단계에서 오류로 차단된다.
- change 제안은 target_node_id가 실제 존재하는 위키 노드 ID여야 한다. 없는 ID면 생성 단계에서 막힌다.
- 승인 단계에서도 content 키를 다시 검증하며, 잘못된 키가 있으면 승인되지 않는다.
- MCP 도구로는 pending 제안까지만 저장하고, 승인·기각·위키 직접 변경은 하지 않는다.
- 위키 본문에는 작성 지침·처리 절차를 그대로 넣지 않는다. content는 주제 내용만 담는다.

### 4-4. 작성 지침의 본문 삽입 금지

- 위키 본문에는 이 스킬의 처리 절차·작성 지침을 그대로 옮기지 않는다.
- 제안 content는 주제 내용만 담고, 스킬 규칙 문구는 넣지 않는다.
- rationale에는 판단 이유만 간결하게 적고, 절차 설명을 반복하지 않는다.

### 4-5. 병합/분리 판단 (제안 단계)

- 기존 위키와 비슷하면 "유사 의심"으로 표시하고, 병합/분리/연결 유지 의견을 제안한다.
- 사용자가 고를 수 있게 제안 형식으로 남기고, 바로 합치지 않는다.

### 4-6. 태그/분류 처리

- 태그가 전혀 없어도 "분류 대기"로 두지 않는다.
- 후보 분류가 있으면 붙이고, 애매하면 후보 여러 개 또는 분류 대기(후보 N개)로 남긴다.
- 임의로 한 카테고리에 확정하지 않는다.

### 4-7. 민감정보/개인정보 처리 원칙

- 개인정보, 비밀번호, 토큰, API 키, 비공개 링크, 사적인 연락처, 비공개 문서 내용 등이 보이면 **정리본 본문에서 드러내지 않는다.**
- 대신 "이 입력에 민감 정보 포함 — 별도 처리 필요" 경고만 남긴다.
- 사용자가 명확히 동의한 경우에만 처리하고, 공유·전송 범위를 확인한다.

## 5. 처리 절차

1. 입력을 읽고 사용자 발언과 AI 제안을 구분한다.
2. 원본 대화의 사용자 발언과 AI 답변 모두 정리하되, 발화자를 구분한다. AI 제안을 사용자 결정이나 검증된 사실로 취급하지 않는다. 원문에 없는 사실·전망은 넣지 않고, 필요하면 추론이라고 표시한다.
3. MCP로 기존 위키/제안을 조회하고(search_wiki, list_proposals, get_wiki_node 등), 들어갈 위치가 있는지 확인한다. 정리할 만한 새 정보가 없으면 새 제안을 만들지 않아도 된다.
4. 새 주제면 add 제안을 만든다. 기존 위키 수정이 필요하면 change 제안을 만든다.
5. change 제안은 실제 대상 위키 node_id가 있을 때만 만든다. node_id가 없으면 생성하지 않는다.
6. content에는 title, summary, body, tags, related만 넣는다. rationale과 target_node_id는 별도 인자로 전달한다.
7. 개인정보/민감 내용은 노출하지 않고 경고만 남긴다.
8. submit_conversation으로 원본을 저장하고, create_proposal로 pending 제안을 저장한다.
9. 승인·기각·위키 직접 변경은 하지 않는다.
10. **새로 생긴 관심사/계속 파볼 것**을 따로 목록화한다.

## 6. 출력

- MCP 제안 흐름 기준 출력:
  - submit_conversation용 원본 저장 제안
  - create_proposal용 pending 제안 (add 또는 change)
  - content 초안 (title, summary, body, tags, related)
- 유사·중복 가능성 있으면 병합/분리/연결 유지 제안
- candidate 분류/태그 후보와 "새로 생긴 관심사·계속 파볼 것" 목록
- 필요하면 rationale 초안 (별도 인자로 넣을 문구)

## 7. 예외 처리

- 입력이 너무 크거나 형식이 들쭉날쭉하면 분할 처리하거나 우선순위를 정해 처리한다.
- 분류가 모호한 항목은 임의로 한 카테고리에 확정하지 않는다.
- 기존 위키/제안이 없으면 새 구조를 제안할 수 있지만, 무조건 새 제안을 만들 필요는 없다.
- MCP 조회·제안 저장 중 문제가 생기면 어디서 막혔는지 명확히 알린다.
- 민감정보/개인정보가 섞인 경우, 정리 대상 포함 여부를 경고하고 실제 저장·전송 방식은 사용자 정책을 따르도록 안내한다.
- 정리할 만한 새 정보가 없으면 새 입력을 따로 제안하지 않아도 된다.

## 8. 호출 시 함께 주면 좋은 것

- 원본 대화 텍스트 또는 제출용 대화 ID
- 이번 입력의 성격 (대화인지, 메모인지, 아이디어 조각인지, 출처 링크가 있는지)
- 기존 위키/제안 조회 결과 (이미 있으면)
- 태그/프로젝트명/관심 설정
- "이번 건 특별히 민감할 수 있다" 같은 힌트
- 필요하면 추가 제안 전에 MCP로 검색·제안 목록부터 확인할 것

## 9. 재사용·확장 팁

- 제안 제목/노드명은 `제목 slug`처럼 일관성 있게 잡으면 연결·병합 판단이 쉬워진다.
- 제안이 쌓이면 pending 제안 목록과 변경 전/후 기준을 함께 확인하면 훑기 좋다.
- 같은 주제가 반복 등장하면 한 위키 노드의 변경 이력과 제안 기록을 함께 보는 방식이 유용하다.
- 나중에 다른 위키 도구/볼트로 옮겨도 제안 기반 수정 방식은 그대로 이어 쓰기 쉽다.
- 항목 간 상호 참조나 링크 관습은 나중에 붙여도 된다. 처음부터 강제할 필요는 없다.

## 10. 민감정보 처리 요약 (한 줄 원칙)

- **민감 내용은 정리본에 쓰지 않는다. 경고만 남긴다.**
- 포함 범위·공유 범위는 사용자 정책을 따른다.
- 동의 없이 민감 내용을 퍼뜨리지 않는다.

## 11. 기존 스킬 대비 차별점

이 스킬은 단순 요약/정리 스킬과 달리,
- 기존 위키 구조가 있으면 **읽고 들어가서 들어갈 위치를 먼저 찾고**, 갱신·병합·분리 의견을 남기며,
- 새 입력마다 **주제 후보를 붙여 분류 대기 상태로 버리지 않고**,
- **원본(raw)과 정리본(wiki)을 분리**하고 덮어쓰기보다 **갱신 이력**을 남기고,
- **새로 생긴 관심사/계속 파볼 것**을 따로 누적한다.

즉, 대화를 한 번 정리해 끝내는 것이 아니라 **쌓이고 연결되고 다시 찾을 수 있는 위키**로 바꾸는 점이 차별점이다.

## 0. 문제정의와 실용성

- **누가/언제**: AI 대화를 자주 하는 일반 사용자, 클로드를 업무·취미·학습·아이디어 정리 등에 쓰는 사람.
- **반복 빈도**: 대화는 매일/매주 발생하지만, 나눈 내용이 위키처럼 누적되지 않아 나중에 다시 찾으려면 채팅 기록을 처음부터 훑어야 하는 일이 반복된다.
- **소요 시간**: 대화 내용을 다시 찾거나 그 때 나눈 아이디어를 다시 정리하는 데 매번 시간이 들고, 비슷한 주제를 다시 처음부터 이야기하는 경우도 생긴다. 대략 대화 1건당 다시 찾는 데 몇 분, 비슷한 주제 재탐색 시 다시 정리하는 데 더 큰 시간이 생길 수 있다.
- **현재 방식 한계**: 채팅 기록은 남아도 주제·관심사가 섞인 채 쌓여서 재사용 가능한 지식으로 이어지지 않는다. 요약만 하면 사라지고, 연결·갱신·추적이 안 남는다.
- **이 스킬로 줄어드는 것**: 다시 찾는 시간, 다시 묻는 시간, 관심사/아이디어가 사라지는 손실, 흩어진 대화를 주제별로 다시 모으는 수고.

# AI 대화 주제별 위키 정리 스킬 (ai-wiki)

## 1. 역할

사용자의 AI 대화·메모·아이디어·링크·떠오른 생각을 **주제별 위키**로 정리해, 다시 찾고 이어 쓸 수 있게 만드는 정리자.

단순 요약이 아니라, **쌓이고 연결되고 갱신되는 위키**를 목표로 한다.
입력마다 다음을 함께 다룬다.

- 주제/프로젝트/관심사 후보를 뽑는다
- 기존 위키 구조가 있으면 들어갈 위치를 먼저 찾는다
- 새 항목이 필요하면 초안(제목·한 줄 요약·핵심·관련 아이디어/링크·연결 후보)을 만든다
- 유사·중복 가능성이 있으면 병합을 강제하지 않고 표시한다
- 태그가 없어도 "분류 대기"로 버리지 않고 후보 분류를 붙인다
- 개인정보/민감 내용은 노출하지 않고 경고만 남긴다
- **새로 생긴 관심사 / 계속 파볼 것**을 따로 목록화한다

## 2. 입력

- AI 대화 텍스트, 복붙 메모, 내보내기 텍스트, 아이디어 조각
- 선택적 태그/프로젝트명/관심 카테고리 (없어도 처리)
- 기존 위키 구조가 있으면 그 구조 (없으면 새로 제안)

## 3. 호출 방식 — 사용자용 프롬프트 세트

아래 세 프롬프트는 사용자가 이 스킬을 부를 때 그대로 복사해 쓸 수 있는 호출 문장이다.
어떤 형태로 불리든 같은 절차로 처리한다.

### 기본형 (가볍게 시작)
> "내가 AI랑 나눴던 대화/메모/아이디어를 주제별 위키로 정리해줘.
> 지금은 태그가 없어도 괜찮고, 네가 주제 후보를 몇 개 잡아서 제안해줘.
> 정리 결과물은 각 주제별 디렉터리 아래에 항목으로 남기고,
> 새로 생긴 관심사나 계속 파볼 만한 것도 따로 표시해줘.
> 민감해 보이는 개인정보는 별도로 표시만 하고 그대로 노출하지 말아줘."

### 구체형 (의견을 더 얹고 싶을 때)
> "다음 AI 대화 내용을 주제별 위키로 정리해줘.
> - 주제 후보 3개 정도를 먼저 제안하고, 내가 고르거나 조정할 수 있게 해줘
> - 각 항목은 제목, 한 줄 요약, 핵심 내용, 관련 아이디어/링크, 연결된 기존 항목 후보 형식으로 남겨줘
> - 비슷한 내용이 이미 있으면 무조건 병합하지 말고, 유사 항목 표시하고 병합/분리 선택권을 줘
> - 태그가 전혀 없는 내용이면 '분류 대기'로 두지 말고 후보 분류를 붙여줘
> - 개인정보/민감해 보이는 내용은 저장 범위를 경고 표시하고, 그대로 퍼뜨리지 말아줘."

### 이미 조금 쌓인 위키에 추가형
> "기존 위키 디렉터리 구조가 이미 있어.
> 새로 들어온 AI 대화/메모를 이 구조에 맞춰서 넣어줘.
> - 어디에 넣을지 먼저 알려주고
> - 새 주제가 필요하면 새 디렉터리/항목 후보와 이유를 제시해줘
> - 기존 항목과 중복 같으면 병합할지 분리할지 의견을 같이 줘
> - 이번 내용에서 '계속 추적해볼 만한 관심사'가 보이면 따로 표시해줘."

## 4. 운영 규칙 (핵심)

이 스킬이 만드는 위키는 **원본과 정리본을 분리**하고, **덮어쓰기보다 갱신 이력**을 우선한다.

### 4-1. 저장소 구조 (기본)

```
위키 루트/
├── README.md                 # 위키 사용법 + 현재 상태 한 줄
├── index.md                  # 한 줄 요약 색인 (주제/항목 목록)
├── tracking.md               # 새로 생긴 관심사 / 계속 파볼 것 누적
├── log.md                    # 이번 정리에서 판단·결정·제안한 내용 기록
├── raw/                      # 원본 입력용 (사용자가 추가, 불변 권장)
│   └── (대화·메모·출처 파일 등)
├── wiki/                     # LLM이 쓰고 유지하는 정리본
│   ├── (주제 디렉터리)/
│   │   ├── (항목 slug).md
│   │   └── ...
│   └── ...
└── schema.md                 # 위키의 규칙/관습/민감정보 원칙 요약
```

- `raw/`는 원본 입력만 둔다. 정리본과 섞지 않는다.
- `wiki/`가 실제 항목들이 사는 곳.
- `index.md`는 "무엇이 어디 있는지"를 빠르게 훑는 용도.
- `tracking.md`는 "이번에 새로 생긴 관심사 / 계속 파볼 것"이 누적되는 곳.
- `log.md`는 이번 정리에서 판단한 내용, 병합/분리 제안, 분류 후보 등을 기록.
- `schema.md`는 위키의 규칙/관습을 요약해 두어, 나중에 이 위키를 다시 열 때도 같은 원칙으로 운영되게 한다.

### 4-2. 원본과 정리본 분리 원칙

- 들어온 대화·메모·아이디어는 가능하면 `raw/`에 원본으로 남긴다(정리가 아니라 입력).
- 정리는 `wiki/`에만 쓴다.
- 같은 내용을 두 번 정리하지 않도록, **이미 wiki/에 있는 주제/항목인지 먼저 확인**한다.

### 4-3. 갱신 방식: 덮어쓰기보다 갱신 이력 우선

- 이미 있는 항목을 다시 만날 때는 무조건 새로 쓰지 않는다.
- 갱신할 때는 기존 내용을 가능한 한 보존하면서, 새 정보/수정/보완을 추가한다.
- 필요하면 항목 안에 "갱신 기록"(날짜 + 무슨 변경이 있었는지)을 남긴다.
- 완전히 다른 방향이면 새 항목으로 분리할 수 있고, 그 판단은 병합/분리 항목으로 남긴다.

### 4-4. 병합/분리 판단 절차 (강제하지 않음)

- 입력이 기존 항목과 비슷해 보이면, "유사 의심"으로 표시한다.
- 바로 합치지 않는다. 다음 중 하나를 제안 형태로 남긴다.
  - 병합: 내용이 같은 주제/맥락이면 한 항목으로 통합
  - 분리: 맥락·목적·대상이 다르면 별도 항목으로 유지
  - 연결만 유지: 항목은 따로 두되 상호 참조
- 판단은 사용자가 고를 수 있게 제안 형식으로 남긴다.
- 실제 병합/분리는 사용자 지시 또는 위키 운영 규칙 범위 안에서만 진행한다.

### 4-5. 태그/분류 처리

- 태그가 전혀 없는 입력이어도 "분류 대기"로 두지 않는다.
- 후보가 있으면 후보 분류를 붙여준다.
- 애매하면 "후보 여러 개" 또는 "분류 대기(후보 N개)"로 남기고 누적 표시한다.
- 임의로 한 카테고리에 확정하지 않는다. 모호한 항목은 그대로 모호하게 남긴다.

### 4-6. 민감정보/개인정보 처리 원칙

- 개인정보, 비밀번호, 토큰, API 키, 내부 코드, 비공개 링크, 사적인 연락처, 비공개 문서 내용 등이 보이면 **정리본 본문에서 드러내지 않는다.**
- 대신 "이 입력에 민감 정보 포함 — 별도 처리 필요" 경고만 남긴다.
- 기본 원칙: 항목 초안에는 민감 내용을 넣지 않고, "이 항목에 민감 정보가 포함되어 있음" 표시만 남긴다.
- 사용자가 명확히 "이것도 저장해줘"라고 동의한 경우에만 처리한다.
- 동의하더라도 공유·전송 범위를 확인한다. 이 위키가 어디에 보관/공유되는지에 따라 처리 방식이 달라질 수 있다.

### 4-7. 추적 대상

- 각 정리 결과에 **"새로 생긴 관심사 / 계속 파볼 것"** 목록을 남긴다.
- 한 번 보고 끝날 내용인지, 계속 추적해볼 만한 관심사인지를 구분하려고 노력한다.
- 추적 후보는 `tracking.md`에 누적한다.

## 5. 처리 절차

1. 입력을 읽고 주제/프로젝트/관심사 후보를 뽑는다.
2. 기존 위키 구조(`wiki/`, `index.md`, `tracking.md` 등)가 있으면 먼저 읽고, 들어갈 위치를 찾는다.
3. 필요하면 `raw/`에 원본을 어떻게 남길지 제안한다.
4. 새 항목이 필요하면 제목, 한 줄 요약, 핵심 내용, 관련 아이디어/링크, 연결 가능한 기존 항목 초안을 만든다.
5. 기존 항목과 비슷하면 유사 의심으로 표시하고, 병합/분리/연결 유지 의견을 제안한다.
6. 태그가 없으면 후보 분류를 붙이고, 애매하면 후보 여러 개/분류 대기로 남긴다.
7. 개인정보/민감 내용은 노출하지 않고 경고만 남긴다.
8. 결과물을 주제별 디렉터리 아래 항목 형태로 `wiki/`에 남긴다.
9. `index.md`, `tracking.md`, `log.md`를 그에 맞춰 갱신한다.
10. **새로 생긴 관심사/계속 파볼 것**을 따로 목록화한다.

## 6. 출력

- 주제별 디렉터리 구조 제시 (또는 갱신 제안)
- 항목 초안 (마크다운 기본; 사용자 선택 가능하면 다른 형식도 가능)
- `index.md` 갱신안 / 색인/태그 목록
- `tracking.md` 갱신안 / "새로 생긴 관심사·계속 파볼 것" 목록
- `log.md` 갱신안 / 이번 정리의 판단·제안 기록
- 병합/분리/분류 후보 제안 목록

## 7. 예외 처리

- 입력이 너무 크거나 형식이 들쭉날쭉하면 분할 처리하거나 우선순위를 정해 처리한다.
- 분류가 모호한 항목은 임의로 한 카테고리에 확정하지 않는다.
- 기존 위키가 없으면 새로 구조를 제안하되, 구조를 무조건 아름답게 만들기보다 재사용 가능성을 우선한다.
- 저장소/디렉터리 접근 문제가 생기면 어디서 막혔는지 명확히 알린다.
- 민감정보/개인정보가 섞인 경우, 정리 대상 포함 여부를 경고하고 실제 저장·전송 방식은 사용자 정책을 따르도록 안내한다.
- "더 이상 갱신할 게 없는데 새 입력만 쌓인" 상태면, 새 입력을 raw/에만 두고 정리는 보류할 수도 있다. 무조건 모든 입력을 wiki/로 옮기지는 않는다.

## 8. 호출 시 사용자가 함께 주면 좋은 것

- 이미 있는 위키 루트 경로 (없으면 새로 제안)
- 이번 입력의 성격 (대화인지, 메모인지, 아이디어 조각인지, 출처 링크가 있는지)
- 태그/프로젝트명/관심이 있으면 그것
- "이번 건 특별히 민감할 수 있다" 같은 힌트

## 9. 재사용·확장 팁

- 항목 파일명은 `제목 slug.md`처럼 일관성 있게 잡으면 연결·병합 판단이 쉬워진다.
- 위키가 쌓이면 `index.md`에 한 줄 요약 색인을 누적하고, `tracking.md`에 관심사 추적을 누적하면 훑기 좋다.
- 같은 주제가 반복 등장하면 한 항목에 "갱신 기록"을 누적하는 방식이 유용하다.
- 나중에 Obsidian/마크다운 볼트처럼 다른 곳으로 옮겨도 이 구조(raw/wiki/색인/추적/로그)는 그대로 쓰기 쉽다.
- 연결 관습(예: 항목 간 상호 참조 표시, 위키링크식 링크)은 나중에 붙여도 된다. 처음부터 강제할 필요는 없다.

## 10. 민감정보 처리 요약 (한 줄 원칙)

- **민감 내용은 정리본에 쓰지 않는다. 경고만 남긴다.**
- 포함 범위·공유 범위는 사용자 정책을 따른다.
- 동의 없이 민감 내용을 퍼뜨리지 않는다.

## 11. 기존 스킬 대비 차별점

이 스킬은 단순 요약/정리 스킬과 달리,
- 기존 위키 구조가 있으면 **읽고 들어가서 들어갈 위치를 먼저 찾고**, 갱신·병합·분리 의견을 남기며,
- 새 입력마다 **주제 후보를 붙여 분류 대기 상태로 버리지 않고**,
- **원본(raw)과 정리본(wiki)을 분리**하고 덮어쓰기보다 **갱신 이력**을 남기고,
- **새로 생긴 관심사/계속 파볼 것**을 따로 누적한다.

즉, 대화를 한 번 정리해 끝내는 것이 아니라 **쌓이고 연결되고 다시 찾을 수 있는 위키**로 바꾸는 점이 차별점이다.

## 1. 개요 (Executive Summary)

### 1.1 제품 설명
사용자가 AI(또는 스킬)와 주고받은 대화를 읽고, **개인화된 주제별 위키**로 정리해 제공하는 **웹 서비스**이다.

이 서비스의 핵심은 다음 네 축이다.

- **Solar Pro 4 기반 서비스 자체 에이전트**: 대화/메모를 읽어 위키 노드 초안과 기존 위키에 대한 변경·병합·분리·연결 제안을 생성한다. 에이전트는 ai-wiki 스킬(ai-wiki-SKILL.md)의 운영 규칙을 지침으로 삼는다.
- **그래프 자동 연결·계층화**: 대화를 자동으로 노드와 관계로 잇고, 주제→하위 주제→엔티티/아이디어로 계층적으로 조직한다. 자동 연결은 **후보**로 제시하고, 실제 반영은 사용자 승인 통제 아래 둔다. AutoSchemaKG의 개념화 기반 스키마 유도 아이디어는 참고하되, 우리 규모에 맞게 재구성한다.

단, LLM/에이전트가 생성한 결과는 위키에 바로 쓰지 않고 **초안/제안(갱신안) 형태로만 제시**하며, 사용자가 **수락**한 내용만 실제 개인 위키에 반영된다. 이렇게 해서 자동 정리·개인화·그래프 구축과 인간 통제(수락/기각/직접 편집)를 함께 제공한다.

개발자뿐 아니라 **AI를 사용하는 모든 사용자**를 대상으로 하며, 기술 지식뿐 아니라 아이디어·결정·계획·배움·회고 등 일상적 지식도 위키 형태로 다룰 수 있어야 한다.

여기서 말하는 **자동 제안/자동 정리**란, 대화 내용을 읽어 위키 노드·제안 후보를 만드는 구간까지를 말하며, 그 후보를 실제 위키에 반영(적용/연동/분리 등)하는 단계는 **사용자 승인**을 거쳐야 한다. 즉, **후보 생성은 자동화된 영역, 실제 반영은 사용자 승인 영역**으로 구분한다.

초기 입력 경로는 다음과 같다.

### 1.2 목표
- [ ] 개발자뿐 아니라 AI를 사용하는 일반 사용자도 부담 없이 쓸 수 있는 낮은 진입장벽과 친근한 경험을 제공한다.
- [ ] 외부 AI 대화를 MCP를 통해 사용자별로 안전하게 수신하고 보관한다.
- [ ] Solar Pro 4와 ai-wiki 스킬이 대화를 읽어 신규 위키 생성, 기존 위키 갱신, 위키 간 연결을 제안한다.
- [ ] 사용자가 변경 내용과 원문 근거를 확인한 뒤 제안을 수락하거나 기각할 수 있도록 한다.
- [ ] 수락된 결과만 개인 위키와 생각 지도에 반영한다.
- [ ] 같은 주제의 후속 대화가 기존 위키의 갱신 제안으로 이어지도록 한다.
- [ ] Solar가 AutoSchema의 스키마 유도 방식을 참고해 노드의 개념적 역할과 관계 유형을 판단하도록 한다.
### 1.3 범위 (In / Out)
|| 포함 (In Scope) | 제외 (Out of Scope) |
|---|---|---|
| AI/스킬과 주고받은 대화를 주제별 위키로 정리 | 단순 채팅 로그 보관만 하고 구조화하지 않는 방식 |
| 새 대화 유입 시 기존 위키 대조 후 추가·변경·분리·연결 제안 (초반 보수적 제안 + 근거 제시) | 근거 없이 연관성만 나열하는 추천 스팸성 기능 |
| 과거 아이디어와 최근 맥락 사이 유용한 관계를 근거와 함께 제시 | 근거 표기 없는 자동 연관성 엔진 |
| 개발자뿐 아니라 일반 사용자도 쓸 수 있는 친근한 인터페이스와 낮은 진입장벽 | 특정 개발 도구/언어 전용 지식베이스로 한정 |

| Solar Pro 4와 ai-wiki 스킬 기반 신규·갱신·연결 제안 | AI가 생성한 내용을 사용자 승인 없이 바로 위키에 반영하는 기능 |
| 변경 전후와 원문 근거를 확인한 뒤 수락·기각 | 제안 내용을 사용자가 직접 편집하는 기능 |
| AutoSchema의 스키마 유도 방식을 참고한 관계 유형 추론 | AutoSchemaKG 전체 파이프라인 및 자동 스키마 데이터베이스 구축 |
| 사용자가 승인한 위키 관계를 생각 지도에 표시 | 승인되지 않은 관계를 자동 확정하는 기능 |
| 위키와 보관 대화에 대한 기본 키워드 검색 | 개인화 랭킹·벡터 검색·그래프 경로 검색 |
| TBD: 추후 사용자 유형별 확장(예: 개인 지식 정리, 팀 공유 등) | 지금 단계에서 확정할 세부 사용자 유형 분류 |

## 2. 문제 정의 (Problem Statement)

### 2.1 배경 / 현황
현재 어떤 상황이 발생하고 있는가? 데이터, 리포트, 사용자 피드백 등 근거 제시.

- AI를 자주 쓰는 사람들은 대화 내용이 쌓이지만, 나중에 다시 찾아보기 어렵다.
- 기록 자체가 흩어져 있으면, 예전 아이디어가 지금 맥락과 연결되는 지점을 놓치기 쉽다.
- 위키로 정리하면 꺼내 쓰기 좋지만, 사람이 매번 정리하기엔 부담이 크다.

### 2.2 해결할 문제
- 문제 1: AI와 주고받은 대화가 기록으로만 남고, 주제별 지식으로 다시 꺼내 쓰기 어렵다.
- 문제 2: 새 대화가 들어와도 기존 기록과 연결되지 않아, 과거 아이디어와의 관계가 표면화되지 않는다.
- 문제 3: 개발자 중심으로만 설계된 도구는 비개발자가 쓰기엔 진입장벽이 높다.

### 2.3 기대 효과
 문제 해결 시 예상되는 정량적/정성적 효과.
- 사용자가 따로 정리하지 않아도 대화 기록이 위키 형태로 남아 재탐색 비용이 낮아진다.
- 새 대화 유입 시 기존 위키와의 관계가 제안되어, 위키가 정적 저장소가 아니라 진화하는 지식 기반이 된다.
- 과거와 현재 맥락 사이의 관계가 근거와 함께 제시되어, 예전 아이디어를 지금 상황에서 다시 활용할 가능성이 높아진다.
- 비개발자도 쓸 수 있는 경험을 제공함으로써, AI를 사용하는 더 넓은 사용자층에게 가치를 전달할 수 있다.
- 대화가 일회성 채팅으로 끝나지 않고 신규 위키 또는 기존 위키의 갱신안으로 누적된다.
- 사용자는 제안의 변경 내용과 원문 근거를 확인한 후 수락 여부를 결정할 수 있다.
- 기존 위키 사이의 관계가 근거와 함께 제안되어, 따로 보관된 생각을 연결해서 볼 수 있다.
- 승인된 관계가 생각 지도에 표시되어 사용자가 자신의 지식 구조를 시각적으로 탐색할 수 있다.

## 3. 목표 사용자 / 페르소나 (Target Users & Personas)

### 3.1 주요 사용자
- **페르소나 1 — AI로 아이디어를 정리하며 일하는 개인 사용자**
  이름/비개발자 예시: 블로그를 쓰거나 공부하거나 기획하는 사람. AI와 자주 대화하지만 기록이 흩어져 나중에 찾기 어려움. 위키로 다시 꺼내 쓰고 싶음.
  주요 니즈: 대화에서 자동으로 주제별 정리, 예전 생각과 지금 생각 사이 연결.
  페인 포인트: 기록할 시간은 부족하고, 쌓아둔 대화는 다시 안 봄.
- **페르소나 2 — 여러 주제에 대해 AI와 대화하며 배우는 사용자**
  예: 학습, 취미, 의사결정, 회고 등 다양한 맥락에서 AI와 소통하는 사람.
  주요 니즈: 기술 중심이 아니라 아이디어·결정·배움 단위로 위키가 생기길 원함.
  페인 포인트: 대화 내용이 많아져도 구조가 없어서 전체 그림이 안 보임.
- **페르소나 3 — (향후 확장) 여러 사람이 AI와 주고받은 맥락을 함께 보고 싶은 소규모 팀/커뮤니티**
  지금은 구체화하지 않고 TBD로 둔다.

### 3.2 사용자 여정 요약
 핵심 터치포인트와 현재 고통 지점.
- 대화 발생 → (현재) 기록이 흩어지고 끝나버림
- 위키 확인 → (현재) 별도 정리 없으면 찾기 어려움
- 새 대화 유입 → 기존 위키와 대조해 연결이 보이지 않음
- 과거 회상 → 예전 아이디어가 지금 맥락과 다시 연결되는 경우가 있어도 표면화되지 않음
→ 이 제품은 이 여정의 각 지점에서 **정리·제안·관계 제시**를 통해 꺼내는 비용을 낮추는 것을 목표로 한다.

## 4. 기능 요구사항 (Functional Requirements)

### 4.1 핵심 기능 (MVP 기준)
 각 기능을 아래 형식으로 정리:

**기능 F1 — 대화 읽어서 위키 노드 만들기**
- 설명: MCP로 전달된 대화 원문을 Solar Pro 4와 ai-wiki 스킬이 분석해 주제별 위키 노드 후보를 만든다. 기존 위키와 같은 주제라면 신규 노드보다 기존 위키 갱신을 우선한다.
- 사용자 스토리: "AI와 나눈 대화 기록을 선택하면, 주제별로 정리된 위키 노드가 자동으로 만들어지면 좋겠다. 그리고 내 과거 맥락/관심사도 좀 반영되면 좋겠다."
- 우선순위: P0
- 입력: MCP를 통해 전달된 대화 원문, 기존 위키 노드
- 출력/결과: 제목, 요약, 본문, 주제, 태그, 분류를 포함한 신규 위키 후보 또는 기존 위키 갱신 제안
- 비고/제약: 생성 결과는 위키에 바로 반영하지 않고 제안 상태로 저장한다.
**기능 F2 — 새 대화 유입 시 기존 위키 대조 후 제안(추가/변경/분리/연결)**
- 설명: 새로운 대화가 들어오면 기존 위키를 검토해, 신규 생성·갱신·연결이 필요해 보이는 내용을 사용자에게 제안한다.
- 사용자 스토리: "새로운 대화를 넣으면 기존 위키를 보고 '이 내용을 여기에 붙이면 좋겠다', '이건 따로 나누는 게 좋겠다' 같은 제안을 해주면 좋겠다."
- 우선순위: P0
- 입력: 새로 들어온 대화, 기존 위키 노드
- 출력/결과:
  - 신규 위키 생성 제안
  - 기존 위키 갱신 제안
  - 기존 위키 간 연결 제안
  - 제안 이유와 원문 근거
  - 갱신 제안의 변경 전후 미리보기
- 비고/제약:
  - 초반에는 가장 신뢰도 높은 제안만 보수적으로 보여준다.
  - 제안은 결과만 던지는 게 아니라, **사용자가 수락하기 전에 무엇이 바뀌는지 알 수 있어야 한다.**
  - 사용자가 수락/기각/수정할 수 있어야 하며, 그 결정과 결과는 다음 새로고침/재접속 후에도 남아 있어야 한다.

**기능 F3 — Solar 기반 동적 관계 스키마 유도 및 연결 제안**

- 설명: Solar Pro 4는 AutoSchema의 데이터 기반 스키마 유도 방식을 참고해 기존 위키 노드와 새 대화에서 노드의 개념적 역할과 관계 유형을 추론한다. 이를 바탕으로 근거가 있는 위키 연결 후보를 생성한다.
- 사용자 스토리: "서로 관련된 위키가 있다면 어떤 관계인지와 왜 연결되는지 확인하고 직접 승인하고 싶다."
- 우선순위: P0
- 입력: 새 대화 원문, 기존 위키 노드, 원문 세그먼트
- 출력/결과:
  - 출발 위키와 도착 위키
  - 각 위키의 개념적 역할
  - 관계 유형
  - 관계 판단 이유
  - 원문 근거
- 제약:
  - 공통 단어 또는 태그가 있다는 이유만으로 연결하지 않는다.
  - 관계의 의미와 원문 근거가 명확하지 않으면 제안하지 않는다.
  - 관계 후보는 제안 목록에만 저장하며 사용자 승인 전에는 확정하지 않는다.
  - 사용자가 수락한 관계만 생각 지도에 표시한다.
- 구현 범위: AutoSchemaKG 전체 라이브러리를 실행하는 것이 아니라, 데이터에서 개념 유형과 관계 유형을 유도한 뒤 관계를 추출하는 핵심 방식을 Solar의 구조화 출력에 적용한다.ㄴ

**기능 F4 — 위키와 보관 대화 검색**
- 설명: 사용자는 키워드로 승인된 위키와 서비스에 보관된 대화를 함께 검색할 수 있다.
- 사용자 스토리: "예전에 저장한 위키나 대화 내용을 키워드로 다시 찾고 싶다."
- 우선순위: P1
- 입력: 사용자의 검색어
- 출력/결과:
  - 검색어가 포함된 위키 노드
  - 검색어가 포함된 보관 대화
  - 검색 결과에서 위키 상세 또는 원본 대화로 이동
- 비고/제약: 개인화 랭킹, 벡터 검색, 그래프 경로 검색은 현재 MVP 범위에 포함하지 않는다.

**기능 F5 — 제안 수락/기각**
- 설명: 사용자는 자동 생성된 제안의 내용과 근거를 검토한 뒤 수락하거나 기각할 수 있다.
- 우선순위: P0
- 출력/결과:
  - 수락된 신규 제안은 위키 노드로 저장
  - 수락된 갱신 제안은 기존 위키와 버전 이력에 반영
  - 수락된 연결 제안은 위키 관계로 저장
  - 기각된 제안은 위키에 반영하지 않음
  - 결정 상태와 시각은 새로고침 후에도 유지
- 제약: 사용자가 제안 내용을 직접 편집하는 기능은 MVP 범위에 포함하지 않는다.

### 4.1.1 데이터 수신/저장/반영 흐름 (MVP)
 MVP에서의 데이터 전달과 위키 반영 흐름을 정의한다.

**(1) 전송 시작 방식 (MVP)**
- MVP에서는 **사용자가 명시적으로 "이 내용을 위키에 저장해줘"라고 요청**할 때 전송을 시작한다.
- 자동 스트리밍/주기 전송/대화 종료 자동 전송 등은 MVP 범위에서 제외한다.
- 전송은 **Solar 기반 에이전트 → 우리 서비스 MCP 도구 호출** 경로로 이뤄진다.
- 사용자는 에이전트와 대화 중 위키 저장 요청을 하고, 에이전트가 그 요청을 받아 MCP 도구로 전달한다.
- 호출 시 **대화 내용(구간 + 맥락)**이 우리 서비스로 전달된다.
- 저장 요청의 해석: 사용자가 "위키에 저장해", "이 내용을 위키에 저장해줘"처럼 말하면 저장 요청으로 해석한다. 별도 확인 없이 `submit_conversation` 호출로 넘어간다.
- 구간 지정 우선: 사용자가 특정 구간을 지정했으면 그 구간만 보낸다. 지정하지 않은 주변을 임의로 덧붙이지 않는다.
- 구간 미지정 시: 구간을 지정하지 않았고 현재 주제가 진행 중이면, 현재 주제와 관련된 대화를 선택해서 보낸다. 선택 기준은 위키에 남길 가치가 있는 내용(주제·아이디어·결정·계획·배움·회고 등)이 포함된 범위, 하나의 주제로 집중된 범위로 묶는다.
- 질문은 불명확할 때만: 어떤 구간인지, 어떤 주제인지 에이전트도 확실히 판단할 수 없을 때만 사용자에게 범위를 확인하는 질문을 한다. 불명확하지 않으면 임의로 질문하지 않는다.
- 보이는 대화만 전송: 에이전트에게 실제로 보이는 대화 내용만 `conversation_text`로 보낸다. 에이전트가 보지 못한 내용이나 누락된 내용을 추론해서 만들어내지 않는다. 대화 기록에서 빠진 부분은 "없음"으로 두거나 비어 있다고 명시할 수는 있어도 없는 대화를 꾸며내지 않는다.
- 저장 요청 없으면 자동 전송하지 않음: 사용자가 위키 저장 요청을 하지 않았으면 `submit_conversation`을 호출하지 않는다. 대화가 끝났어도 자동으로 전송하지 않는다. MVP에서는 명시적 저장 요청만 전송 트리거로 본다.
- 에이전트 지침 연결 위치 누락 보고: 에이전트 지침에서 "위키에 저장하라", "submit_conversation을 호출하라" 같은 명시적 연결 위치를 찾을 수 없으면 그 사실을 보고한다. 지침 어딘가에 저장 요청 처리 방식이 연결되어 있어야 하며, 연결이 없으면 임의로 행동을 만들어내지 않고 누락 사실을 알린다.
- 입력 구조/저장 로직 변경 없음: 이번 작업에서 `submit_conversation`의 입력 파라미터 구조(`session_id`, `conversation_text`, `context`)나 실제 저장 로직은 바꾸지 않는다. 여기서 정리하는 것은 도구 설명의 해석과 에이전트 지침 관점의 저장·요청 규칙이다.

**(2) 전송 단위 및 입력 계약 (MVP)**

MVP에서 submit_conversation은 대화의 **역할 구분 메시지 목록(messages)** 또는 기존 **대화 텍스트(conversation_text)** 중 하나로 원문 구간을 전달한다. 두 입력이 함께 올 수도 있으며, 그 경우 아래 불일치 규칙을 따른다.

- **기본 입력 (기존, 계속 지원)**
  - `session_id: str` — 대화/세션을 식별하는 ID (필수)
  - `conversation_text: str` — 전송할 대화 원문(구간). messages가 없을 때 사용 (선택, messages와 상호보완)
  - `context: dict` — 보충 맥락. 주제, 스킬, 세션 유형, 앞뒤 흐름 등 전송 단위를 이해할 때 필요한 정보 (선택)

- **추가 입력 (신규)**
  - `messages: list[dict]` — 역할이 구분된 메시지 목록. conversation_text 대신 또는 함께 사용.
    - 각 메시지 필수: `role: str`, `content: str`
    - 각 메시지 선택: `record_id: str`(원본 메시지 식별자), `timestamp: str`(ISO 8601 시각)
    - role 예시: "user", "assistant", "system", "tool" 등. 서비스/에이전트가 실제 관측한 역할값만 사용한다.
  - `source: str` — 이 전송의 출처/종류 구분. 예: "mcp", "agent", "user_direct" 등. 저장 시 출처 추적에 사용 (선택)

- **입력 계약 원칙**
  - role과 content는 각 메시지의 필수 필드다. 둘 중 하나라도 누락되면 도구 오류로 처리한다.
  - `record_id`, `timestamp`는 선택이며, 실제로 알 수 있는 값만 넣는다.
  - 알 수 없는 원본 id나 시각을 추측해서 만들어 넣지 않는다. 모르는 값은 넣지 않거나 비워 둔다.
  - messages가 제공되면 그것이 원문 구간의 1차 출처가 된다. conversation_text만 제공된 경우는 기존 방식대로 처리한다.
  - messages와 conversation_text가 함께 제공되면 불일치 검사를 수행한다 (아래 규칙).

- **messages와 conversation_text 동시 입력 시 불일치 처리 규칙**
  - messages에서 각 메시지의 content를 역할 정보와 함께 연결한 재구성 텍스트와 conversation_text를 비교한다.
  - 비교는 앞뒤 공백/개행 정도를 정규화한 뒤 수행한다.
  - 두 텍스트가 실질적으로 같으면 정상 처리한다.
  - 두 텍스트가 다르면 도구 오류로 처리하고, 어느 쪽이 원본인지 애매하면 messages를 우선하되 차이를 오류로 보고한다.
  - messages 없이 conversation_text만 있는 경우는 기존과 동일하게 처리한다.

- **전송 범위와 선택 방식**
  - 메시지에 포함할 범위는 사용자가 지정한 구간 또는 에이전트 지침에서 정한 선택 기준에 따른다(PRD 4.1.1 (1) 참조).
  - 구간을 지정하지 않았고 현재 주제가 진행 중이면, 에이전트가 현재 주제와 관련된 메시지를 선택해 messages로 구성한다.
  - 선택 시 역할 구분을 유지하고, 실제 관측한 content만 넣는다.

- **보충 맥락 (context)**
  - context는 messages/conversation_text와 별개로, 해당 구간이 어떤 주제/스킬/세션에서 나왔는지, 앞뒤 흐름 등 보충 정보를 담는다.
  - context에 대화 원문 자체를 넣지 않는다(원문은 messages 또는 conversation_text에 있다).

- **예시 (정상 요청, messages 방식)**
  ```json
  {
    "session_id": "sess-12345",
    "source": "agent",
    "messages": [
      { "role": "user", "content": "동네 산책 사진으로 사진집을 만들까 고민 중이야.", "record_id": "msg-001", "timestamp": "2026-09-15T10:00:00+09:00" },
      { "role": "assistant", "content": "사진집은 인쇄와 전자책 두 가지 형식이 있어요. 어떤 쪽으로 생각하세요?", "record_id": "msg-002", "timestamp": "2026-09-15T10:00:15+09:00" },
      { "role": "user", "content": "아직 정리는 안 됐고, 일단 아이디어만 보관해두고 싶어.", "record_id": "msg-003", "timestamp": "2026-09-15T10:00:30+09:00" }
    ],
    "context": { "topic": "사진집 기획", "skill": "ai-wiki" }
  }
  ```

- **예시 (정상 요청, conversation_text 방식, 기존 호환)**
  ```json
  {
    "session_id": "sess-12345",
    "conversation_text": "사용자: 동네 산책 사진으로 사진집을 만들까 고민 중이야.\nAI: 사진집은 인쇄와 전자책 두 가지 형식이 있어요. 어떤 쪽으로 생각하세요?\n사용자: 아직 정리는 안 됐고, 일단 아이디어만 보관해두고 싶어.",
    "context": { "topic": "사진집 기획", "skill": "ai-wiki" }
  }
  ```

- **예시 (messages + conversation_text 동시, 정상 케이스)**
  ```json
  {
    "session_id": "sess-12345",
    "source": "agent",
    "messages": [
      { "role": "user", "content": "동네 산책 사진으로 사진집을 만들까 고민 중이야." },
      { "role": "assistant", "content": "사진집은 인쇄과 전자책 두 가지 형식이 있어요. 어떤 쪽으로 생각하세요?" }
    ],
    "conversation_text": "사용자: 동네 산책 사진으로 사진집을 만들까 고민 중이야.\nAI: 사진집은 인쇄과 전자책 두 가지 형식이 있어요. 어떤 쪽으로 생각하세요?",
    "context": { "topic": "사진집 기획", "skill": "ai-wiki" }
  }
  ```
  위처럼 재구성 텍스트와 conversation_text가 실질적으로 같으면 허용한다. 다르면 오류로 처리한다.

- 이번에 `submit_conversation` 입력 구조가 messages/source를 지원하도록 확장된다. 기존 `conversation_text` 기반 호출은 계속 지원한다.

**(3) 전달 후 보관 (MVP)**
- 전달받은 기록은 먼저 **보관**한다.
- 보관은 위키 반영과 분리해서 생각해야 하며, 나중에 정리/제안/검색에 쓸 수 있는 원본성 기록으로 남긴다.
- 보관은 두 층으로 생각할 수 있다.
  - 서비스 수신 원본: MCP 도구로 전달받은 대화 내용(구간 + 맥락) 자체를 보관하는 층
  - 사용자 추가 원본: 사용자가 직접 덧붙이거나 외부에서 가져온 원본
- 보관한 기록은 곧바로 위키로 바꾸기보다, **Solar + ai-wiki 스킬이 이를 읽어 위키 생성/변경 후보를 만드는 입력**으로 사용한다.
- MVP에서는 원본과 정리본이 섞이지 않게 관리하는 것이 중요하다.

**(4) 위키 생성/변경 제안 (MVP)**
- 우리 서비스는 전달받은 대화 내용(구간 + 맥락)을 바탕으로 **Solar + ai-wiki 스킬로 위키 생성/변경/추가/분리/연결 제안을 만든다.**
- 제안은 결과만 던지지 않고, 적용 시 무엇이 바뀌는지(변경 전/후)를 함께 보여줘야 한다.

**(5) 사용자 확인 및 선택 반영 (MVP)**
- 사용자는 제안을 확인한 뒤, 변경 전/후를 보고 수용/기각 등 선택한다.
- 반영은 사용자 선택에 따라 이뤄지며, 결정과 결과는 새로고침/재접속 후에도 남아야 한다.
- 자동 제안이 곧바로 반영되는 구조가 아니라, **보관 → 후보 생성 → 제안 → 사용자 확인 → 사용자 선택 반영** 순서로 진행된다.

**(6) MVP에서 다루지 않는 것 (범위 제한)**
- 전체 대화를 항상 통째로 보내는 방식
- 자동 재전송/주기 동기화
- 사용자 요청 없이 대화 종료 시 자동 위키화
- 위와 같은 방식은 이후 고도화 검토 대상으로 남겨둔다.
 우선순위가 낮은 기능 또는 2차 릴리즈 후보.
- 위키 노드 단위/타입 확장(예: 아이디어, 결정, 계획, 배움, 회고 등)
- 사용자 유형별 경험 세분화(개인 지식 정리, 팀 공유 등)
- 위키 공유/협업 기능
- 더 정교한 관계 그래프 시각화
- 사용자 피드백을 활용한 제안 품질 지속 개선

## 5. 비기능 요구사항 (Non-Functional Requirements)

| 항목 | 요구사항 |
|---|---|
| 성능 (응답 시간, 처리량 등) | 위키 열람과 제안 제시는 사용자가 기다림을 느끼지 않는 수준이어야 함. 대화 파싱/요약/대조는 백그라운드 또는 비동기 처리 검토 |
| 보안 (인증, 저장 데이터 암호화 등) | 사용자 대화/지식 데이터는 민감할 수 있으므로 저장·전송 시 적절한 보호 필요. 사용자별 데이터 격리 필수 |
| 가용성 / SLA | MVP 기준으로는 핵심 위키 열람/제안은 안정적으로 제공되어야 함 |
| 확장성 | 위키 노드와 관계가 늘어나도 탐색/제안이 무너지지 않도록 구조 설계 필요 |
| 호환성 (브라우저, OS, 디바이스) | 웹 기반이라면 주요 브라우저에서 정상 동작해야 함 |
| 접근성 | 비개발자 사용자도 쓰므로 읽기/탐색/제안을 이해하기 쉬워야 함 |
| 로깅 / 모니터링 | 제안 수용/기각, 위키 조회 등 핵심 행동 로그를 남겨 품질 개선에 활용 |
| 규제 / 컴플라이언스 | 사용자 데이터 처리 관련 요구사항이 있으면 반영 |

## 6. 사용자 경험 / UI 요구사항 (UX / UI Requirements)

### 6.1 주요 화면 / 플로우
 화면별 흐름을 기술하거나 와이어프레임/프로토타입 링크 첨부.
- 대화 입력/가져오기 화면
- 위키 허브(주제별 노드 목록)
- 개별 위키 노드(내용 + 관련 제안 + 관계 제안)
- 제안 수용/기각/수정 인터페이스

### 6.2 디자인 원칙
- **낮은 진입장벽**: 개발자뿐 아니라 AI를 쓰는 일반 사용자도 처음 보고 이해할 수 있어야 함.
- **명료성**: 추가/변경/분리/연결 같은 개념도 너무 무겁지 않게, 짧고 직관적으로 표현.
- **통제감**: 자동 정리가 기본이지만 사용자가 수락/기각/직접 편집할 수 있어야 함.
- **자동과 승인의 분리**: 대화 읽기, 위키 후보/제안 후보 생성은 자동화 구간이고, 실제 위키에 반영(추가/변경/연결/분리 등)은 사용자 승인 구간에서 이뤄지도록 설계한다. 자동 제안이 곧바로 반영되는 구조가 아니라, 승인 전후로 변경 전/후를 확인하고 결정하게 한다.
- **근거 투명성**: 관계/제안을 제시할 때 왜 그런지 근거를 함께 보여줘야 신뢰를 얻음.
- **과도한 자동화 회피**: 초반에는 신뢰 높은 제안만 보수적으로 보여주고, 사용자에게 피로가 쌓이지 않게 함.

### 6.3 에러 / 예외 처리
 주요 에러 케이스와 사용자에게 보여줄 안내 방식.
- 대화/스킬 데이터를 읽지 못할 때
- 위키 구조가 아직 비어 있거나 너무 적을 때
- 제안의 근거가 약해서 표시하지 않는 경우의 처리 방식(묵살 or "현재 근거 충분치 않음" 표기)

## 7. 데이터 모델 / API (Data Model & API)

### 7.1 핵심 엔티티
 주요 엔티티와 관계 요약 (ERD 스케치 또는 링크).
- 사용자
- 대화/스킬 출처(대화 묶음, 세션 등)
- 위키 노드(주제/엔티티 단위)
- 위키 노드 내용(요약, 발췌, 메타데이터)
- 관계/제안(추가, 변경, 분리, 연결, 관계 제시 등)
- 제안 상태/승인 이력(제안 후보, 변경 전/후 미리보기, 수용/기각, 반영 결과, 결정 시점)
|- 사용자 피드백(수용/기각/수정 등)

※ 제안 후보는 "생성됨"과 "승인/기각/반영됨" 상태를 구분해 관리해야 한다.
자동으로 만든 후보와 실제 위 키에 반영된 결과를 혼동하지 않도록, 제안→승인→반영 흐름을 별도 상태/이력으로 추적한다.

### 7.1.1 위키 저장 구조 (MVP)
 전달받은 대화가 어떤 위키로 저장되는지 정의한다.

**(1) 원본 보관과 위키 정리본 분리 (MVP)**
- 전달받은 대화/맥락 기록은 먼저 **원본 보관 영역**에 남긴다.
- 위키 정리본은 원본과 분리된 영역에 저장한다.
- 원본은 입력 당시의 기록을 보존하는 용도이고, 위키 정리본은 꺼내 읽기 좋게 재구성한 결과물이다.
- MVP에서는 원본과 정리본이 섞이지 않게 관리하는 것이 중요하다.

**(2) 위키 노드 저장 방식 (MVP)**
- 위키는 **주제/엔티티 단위의 노드**로 저장한다.
- 각 노드는 제목, 한 줄 요약, 핵심 내용, 관련 아이디어/링크/연결 후보 같은 기본 항목을 가진다.
- 새 대화 구간은 대화 전체를 무조건 하나의 노드로 만드는 방식이 아니라, 내용 성격에 따라 위키 노드로 정리한다.
- 같은 주제가 이미 있으면 별도 노드를 무작정 만들지 않고, 기존 노드에 병합할지/분리할지/연결만 유지할지 제안한다.

**(3) 대화 구간 → 위키 노드 매핑 (MVP)**
- 사용자가 지정한 대화 구간은 **맥락과 함께** 전달되므로, 위키 노드는 "단편 문장"이 아니라 "맥락이 있는 내용 단위"를 반영한다.
- 하나의 대화 구간이 여러 위키 노드에 걸쳐 관련될 수 있고, 반대로 한 위키 노드가 여러 대화 구간에서 보강될 수 있다.
- 이 관계를 추적 가능하게 남겨야, 나중에 어떤 대화에서 어떤 위키 노드가 보강됐는지 확인할 수 있다.

**(4) 갱신/누적 방식 (MVP)**
- 같은 위키 노드를 다시 만날 때는 무조건 새로 만들지 않는다.
- 새 내용이 들어오면 기존 내용을 가능한 한 보존하면서 갱신/보완을 추가한다.
- 필요하면 갱신 기록(언제, 어떤 변경이 있었는지)을 남긴다.
- 방향이 다른 내용은 새 노드로 분리할 수 있고, 그 판단은 병합/분리 제안으로 남긴다.

**(5) 위키 저장 시 명시할 것 (MVP)**
- 어떤 원본 대화 구간이 어떤 위키 노드에 반영됐는지
- 어떤 변경이 있었는지(변경 전/후)
- 제안이 수용됐는지/기각됐는지
- 위키가 자동 반영된 것이 아니라 사용자 선택에 따라 반영됐는지

※ 세부 스키마와 저장 형식은 MVP 설계 단계에서 확정한다.

## 8. 성공 지표 (Metrics & KPIs)

### 8.1 MVP 성공 기준

- MCP로 제출한 대화가 사용자 계정의 유입 기록에 저장된다.
- 제출된 대화에서 최소 한 개 이상의 신규·갱신·연결 제안을 생성할 수 있다.
- 신규 제안을 수락하면 내 위키에 노드가 생성된다.
- 같은 주제의 후속 대화가 기존 위키 갱신 제안으로 이어진다.
- 연결 제안을 수락하면 생각 지도에 두 위키의 관계선이 표시된다.
- 기각한 제안은 위키에 반영되지 않는다.
- 새로고침 후에도 위키와 결정 상태가 유지된다.

### 8.2 추적 방법
 어떤 도구/센서로 측정할 것인가 (이벤트, 분석 도구 등).
- 위키 열람, 노드 클릭, 제안 노출/수락/기각, 관계 제시 노출/클릭 등 이벤트 설계
- 초기엔 과도한 이벤트보다 핵심 행동 위주 추적

## 9. 리스크 & 의존성 (Risks & Dependencies)

| 리스크 | 설명 | 완화 방안 |
|---|---|---|
| 제안 품질이 낮으면 스팸처럼 느껴질 수 있음 | 근거 부실/과도한 제안은 신뢰를 떨어뜨림 | 초반 보수적 제안, 근거 표기, 사용자 피드백 반영 |
| 자동 정리가 사용자의 통제감을 약화시킬 수 있음 | 위키가 사용자 의도와 다르게 정리될 수 있음 | 수락/기각/직접 편집 제공, 위키 수정의 자유도 확보 |
| 대화가 너무 적으면 위키/제안이 빈약할 수 있음 | 초기 데이터 부족 시 가치 체감이 어려움 | 비어 있는 상태 UX 고려, 점진적 적립 경험 설계 |
| 비개발자 사용자에게 개념이 어렵게 느껴질 수 있음 | 추가/변경/분리/연결 같은 표현이 부담될 수 있음 | 친근한 표현, 짧은 설명, 점진적 노출 |

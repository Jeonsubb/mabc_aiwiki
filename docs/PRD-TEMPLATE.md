## 1. 개요 (Executive Summary)

### 1.1 제품 설명
사용자가 AI(또는 스킬)와 주고받은 대화를 읽고, 주제별 위키로 정리해 제공하는 **웹 서비스**이다.
이 서비스의 백엔드 LLM은 ai-wiki 스킬(ai-wiki-SKILL.md)의 운영 규칙을 지침으로 삼아,
대화/메모를 주제별 위키 노드 초안과 기존 위키에 대한 변경·병합·분리·연결 제안으로 변환한다.
단, LLM이 생성한 결과는 위키에 바로 쓰지 않고 **초안/제안(갱신안) 형태로만 제시**하며,
사용자가 **승인/기각/수정**한 내용만 실제 개인 위키에 반영된다.
이렇게 해서 자동 정리와 인간 통제(수락/기각/직접 편집)를 함께 제공한다.

**초기 타겟(초점)**
AI로 기획·콘텐츠 작업을 자주 하는 개인 사용자.
예: 블로그/콘텐츠 기획, 프로젝트 구상, 업무 아이디어 정리처럼 AI와 대화하면서 생각을 발전시키는 개인 사용자.
선정 근거: AI와 주고받은 대화 속에서 아이디어, 결정, 작업 방향이 계속 만들어지지만 그 내용이 대화 기록으로 흩어지기 쉬워 다시 꺼내 쓰기 어렵다. 이 제품은 그런 대화를 주제별 위키로 정리하고 새 대화가 들어오면 기존 위키와 연결해 제안하므로, 이 타겟의 재탐색/재사용 문제를 직접 줄여준다.

**추후 확장 방향**
- 학습 사용자: 공부, 개념 정리, 질문-답변 누적 등 AI와 학습 맥락에서 소통하는 사용자
- 취미/개인 관심사 사용자: 취미, 아이디어 탐색, 일상 메모 등 다양한 주제로 AI와 소통하는 사용자
- 팀/소규모 공유 사용자: 여러 사람이 AI와 주고받은 맥락을 함께 보거나, 개인 위키를 팀 맥락에서 활용하려는 사용자
- 일반 사용자: 특별한 전문 작업보다 AI를 자주 쓰는 일반 개인 사용자

※ 지금 단계에서는 확장 대상별 세부 설계를 구체화하지 않고, MVP 검증 이후 단계적으로 검토한다.

**사용 전/후 대비**
- 사용 전: AI와의 대화는 기록으로 남지만, 주제별 지식으로 다시 꺼내 쓰기 어렵고 예전 아이디어·결정 이유·작업 맥락을 현재 작업에 다시 활용하기 어렵다.
- 사용 후: 대화 구간과 맥락을 기반으로 위키 후보가 만들어지고, 기존 위키와의 관계(제안)와 과거-최근 맥락 사이의 관계가 근거로 제시되므로, 예전 아이디어를 지금 상황에서 다시 확인·연결·활용하기 쉬워진다.

이 제품은 단순 요약/보관이나 "대화 내용을 그대로 저장"하는 방식과 다르게,
**기존 위키를 읽고 들어가 위치·병합·분리 의견을 제시하고, 새 입력마다 주제 후보를 붙여 연결과 갱신을 이어가는 방식**을 지향한다.
그 결과 대화 기록이 한 번 정리로 끝나는 것이 아니라, 다시 찾고 이어 쓸 수 있는 위키로 바뀐다.

개발자뿐 아니라 **AI를 사용하는 모든 사용자**를 대상으로 하며,
기술 지식뿐 아니라 아이디어·결정·계획·배움·회고 등 일상적 지식도 위키 형태로 다룰 수 있어야 한다.

여기서 말하는 **자동 제안/자동 정리**란, 대화 내용을 읽어 위키 노드·제안 후보를 만드는 구간까지를 말하며,
그 후보를 실제 위 키에 반영(적용/연동/분리 등)하는 단계는 **사용자 승인**을 거쳐야 한다.
즉, **후보 생성은 자동화된 영역, 실제 반영은 사용자 승인 영역**으로 구분한다.

초기 입력 경로는 다음과 같다.
- Solar 기반 에이전트에서 사용자와 대화가 진행된다.
- 사용자가 위키 저장을 요청하면 에이전트가 우리 서비스의 MCP 도구를 호출한다.
- 호출 시 대화 내용(구간 + 맥락)을 그대로 우리 서비스로 전달한다.
- 우리 서비스는 Solar + ai-wiki 스킬로 위키 생성/변경 제안을 만든다.
- 사용자는 그 제안을 확인한 뒤, 자신의 선택에 따라 위키에 반영한다.

### 1.2 목표
- [ ] 흩어진 대화 기록을 주제별 위키로 자동 편성해, 나중에 꺼내 쓰기 쉬운 지식으로 바꾼다.
- [ ] 새 대화가 들어올 때 기존 위키와의 관계(추가/변경·분리·연결)를 제안하고, 사용자가 각 제안을 **승인/기각**하면서 위키가 사용자의 결정에 따라 갱신되도록 한다.
- [ ] 과거와 최근 맥락 사이의 유용한 관계를 근거와 함께 제시해, 예전 아이디어가 지금 상황에서 다시 의미를 갖게 한다.
- [ ] 개발자뿐 아니라 AI를 사용하는 일반 사용자도 부담 없이 쓸 수 있는 낮은 진입장벽과 친근한 경험을 제공한다.

### 1.3 범위 (In / Out)
| 포함 (In Scope) | 제외 (Out of Scope) |
|---|---|
| AI/스킬과 주고받은 대화를 주제별 위키로 정리 | 단순 채팅 로그 보관만 하고 구조화하지 않는 방식 |
| 새 대화 유입 시 기존 위키 대조 후 추가·변경/분리·연결 제안 (초반 보수적 제안 + 근거 제시) | 근거 없이 연관성만 나열하는 추천 스팸성 기능 |
| 과거 아이디어와 최근 맥락 사이 유용한 관계를 근거와 함께 제시 | 근거 표기 없는 자동 연관성 엔진 |
| 개발자뿐 아니라 일반 사용자도 쓸 수 있는 친근한 인터페이스와 낮은 진입장벽 | 특정 개발 도구/언어 전용 지식베이스로 한정 |
| 사용자가 제안을 수락/기각/직접 편집하며 통제 가능 | 사용자가 수정할 수 없는 완전 자동 위키 |
| TBD: 추후 사용자 유형별 확장(예: 개인 지식 정리, 팀 공유 등) | 지금 단계에서 확정할 세부 사용자 유형 분류 |

※ 세부 사용자 유형과 위키 구조는 페르소나/데이터 모델 확정 후 구체화한다.

## 2. 문제 정의 (Problem Statement)

### 2.1 배경 / 현황
- AI를 자주 쓰는 사람, 특히 기획·콘텐츠 작업을 하는 개인 사용자는 대화 내용이 자주 쌓이지만, 나중에 다시 찾아보거나 활용하기 어렵다.
- 과거 아이디어, 결정 이유, 작업 맥락이 여러 대화에 흩어져 있어, 현재 작업에서 다시 참고하거나 이어 쓰기 어렵다.
- 같은 주제나 결정을 다시 이야기하게 되는 경우가 생기고, 이전에 어떤 이유로 그렇게 정했는지 기억하지 못해 처음부터 다시 정리하게 된다.
- 위키로 정리하면 꺼내 쓰기 좋지만, 사람이 매번 정리하기엔 부담이 크고, 흩어진 대화를 구조화하는 것도 만만치 않다.

### 2.2 해결할 문제
- 문제 1: AI와 주고받은 대화가 기록으로만 남고, 주제별 지식으로 다시 꺼내 쓰기 어렵다. 특히 여러 대화에 흩어진 과거 아이디어와 결정 이유, 작업 맥락을 현재 작업에 다시 활용하기 어렵다. 메모/요약/단순 저장만으로는 대화 속에서 왜 그런 결정을 했는지, 어떤 아이디어가 이어졌는지까지 다시 꺼내기 어렵고, 새 작업에서 과거 맥락을 의도적으로 끌어다 쓰기도 힘들다.
- 문제 2: 새 대화가 들어와도 기존 기록과 연결되지 않아, 과거 아이디어와의 관계가 표면화되지 않는다. 예전 아이디어와 지금 작업 사이의 유용한 연결을 놓치기 쉽다.
- 문제 3(UX): 폴더·태그·위키 구조를 미리 설계하지 않으면 시작하기 어렵게 느껴질 수 있어, 초기 구조를 미리 정해두지 않고도 자연스럽게 위키 쌓기를 시작할 수 있어야 한다. 즉, 위키 구조를 처음부터 잘 갖춰야 한다는 부담을 줄여야 한다.

### 2.3 기대 효과
 문제 해결 시 예상되는 정량적/정성적 효과.
- 사용자가 따로 정리하지 않아도 대화 기록이 위키 형태로 남아 재탐색 비용이 낮아진다.
- 새 대화 유입 시 기존 위키와의 관계가 제안되어, 위키가 정적 저장소가 아니라 진화하는 지식 기반이 된다.
- 과거와 현재 맥락 사이의 관계가 근거와 함께 제시되어, 예전 아이디어를 지금 상황에서 다시 활용할 가능성이 높아진다.
- 비개발자도 쓸 수 있는 경험을 제공함으로써, AI를 사용하는 더 넓은 사용자층에게 가치를 전달할 수 있다.
- 단순 요약/보관 방식에서 벗어나, 기존 위키와 연결되며 쌓이고 갱신되는 위키 경험으로 바뀐다.

## 3. 목표 사용자 / 페르소나 (Target Users & Personas)

### 3.1 주요 사용자
- **초기 타겟(초점) — AI로 기획·콘텐츠 작업을 자주 하는 개인 사용자**
  예시: 블로그/콘텐츠 기획, 프로젝트 구상, 업무 아이디어 정리처럼 AI와 대화하면서 생각을 발전시키는 개인 사용자.
  선정 근거: AI와 주고받은 대화 속에서 아이디어, 결정, 작업 방향이 계속 만들어지지만, 그 내용이 대화 기록으로 흩어지기 쉬워 다시 꺼내 쓰기 어렵다. 이 제품은 그런 대화를 주제별 위키로 정리하고, 새 대화가 들어오면 기존 위키와 연결해 제안하므로 이 타겟의 재탐색/재사용 문제를 직접 줄여준다.
  주요 니즈: AI와 주고받은 대화/아이디어를 주제별 위키로 정리해서 다시 꺼내 쓰고 싶음. 예전 생각과 지금 생각 사이의 연결도 보고 싶음.
  페인 포인트: 대화 기록은 쌓이지만 구조가 없어서 다시 찾기 어렵고, 비슷한 주제를 처음부터 다시 이야기하게 됨. 기록할 시간은 부족하고 쌓아둔 대화는 잘 안 보게 됨.

※ MVP는 위 초기 타겟(개인 사용자 중심)에 집중해 설계한다. 이후 확장은 아래 방향으로 단계적으로 검토한다.
  - 학습 사용자: 공부, 개념 정리, 질문-답변 누적 등 AI와 학습 맥락에서 소통하는 사용자
  - 취미/개인 관심사 사용자: 취미, 아이디어 탐색, 일상 메모 등 다양한 주제로 AI와 소통하는 사용자
  - 팀/소규모 공유 사용자: 여러 사람이 AI와 주고받은 맥락을 함께 보거나, 개인 위키를 팀 맥락에서 활용하려는 사용자
  - 일반 사용자: 특별한 전문 작업보다 AI를 자주 쓰는 일반 개인 사용자
※ 지금 단계에서는 확장 대상별 세부 설계를 구체화하지 않고, MVP 검증 이후 단계적으로 검토한다.

### 3.2 사용자 여정 요약
 핵심 터치포인트와 현재 고통 지점.
- 대화 발생 → (현재) 기록이 흩어지고 끝나버림
- 위키 확인 → (현재) 별도 정리 없으면 찾기 어려움
- 새 대화 유입 → 기존 위키와 대조해 연결이 보이지 않음
- 과거 회상 → 예전 아이디어가 지금 맥락과 다시 연결되는 경우가 있어도 표면화되지 않음
→ 이 제품은 이 여정의 각 지점에서 **정리·제안·관계 제시**를 통해 꺼내는 비용을 낮추는 것을 목표로 한다.

## 4. 기능 요구사항 (Functional Requirements)

### 4.1 핵심 기능 (MVP 기준)
 각 기능을 아래 형식으로 정리:

**기능 F1 — 대화 읽어서 위키 노드 만들기**
- 설명: 사용자가 AI(또는 스킬)와 주고받은 대화를 읽어, 주제별 위키 노드 후보를 만든다.
- 사용자 스토리: "AI와 나눈 대화 기록을 선택하면, 주제별로 정리된 위키 노드가 자동으로 만들어지면 좋겠다."
- 우선순위: P0
- 입력: 대화/스킬에서 전달된 텍스트 또는 대화 이력. MVP에서는 Solar 기반 에이전트에서 위키 저장 요청 시 전달된 대화 내용(구간 + 맥락)을 입력으로 사용한다.
- 출력/결과: 주제별 위키 노드 후보(노드 제목, 내용 요약, 연결 가능한 관련 노드 후보)
- 비고/제약: 초반에는 구조보다 "꺼내서 읽기 쉬운 단위"를 만드는 데 집중. 기술 용어에 한정되지 않은 일반 주제도 다룰 수 있어야 함. ai-wiki 스킬의 운영 규칙을 지침으로 삼아 초안/제안 형태로 생성한다.

**기능 F2 — 새 대화 유입 시 기존 위키 대조 후 제안(추가/변경/분리·연결)**
- 설명: 새로운 대화가 들어오면 기존 위키를 검토해, 추가·변경·분리·연결이 필요해 보이는 내용을 사용자에게 제안한다.
- 사용자 스토리: "새로운 대화를 넣으면 기존 위키를 보고 '이 내용을 여기에 붙이면 좋겠다', '이건 따로 나누는 게 좋겠다' 같은 제안을 해주면 좋겠다."
- 우선순위: P0
- 입력: 새로 들어온 대화, 기존 위키 노드
- 출력/결과:
  - 제안 목록(추가/변경·분리·연결 후보) + 각 제안에 대한 근거
  - 각 제안별로 **적용 시 바뀌는 위키 노드/내용과 변경 전/후 미리보기**를 함께 제시
  - 모든 제안은 반드시 수용/기각 버튼 또는 승인 흐름을 거쳐야 하며, 각 제안은 수용/기각 결정을 받는다
- 비고/제약:
  - 초반에는 가장 신뢰도 높은 제안만 보수적으로 보여준다.
  - 제안은 결과만 던지는 게 아니라, **사용자가 수락하기 전에 무엇이 바뀌는지 알 수 있어야 한다.**
  - 사용자가 수락/기각/수정할 수 있어야 하며, 그 결정과 결과는 다음 새로고침/재접속 후에도 남아 있어야 한다.
  - ai-wiki 스킬이 생성한 초안을 바탕으로 서비스 쪽에서 변경 전/후와 근거를 정리해 제시한다.

**기능 F3 — 과거 아이디어와 최근 맥락 사이의 유용한 관계 제시 + 근거**
- 설명: 과거와 최근 대화 맥락 사이에 유용한 관계가 보이면, 그 근거와 함께 관계를 제시한다.
- 사용자 스토리: "예전에 했던 생각이 지금 대화와 연결되면, 왜 연결되는지 근거를 함께 보여주면 좋겠다."
- 우선순위: P0
- 입력: 과거 위키 노드/대화, 최근 대화 맥락
- 출력/결과: 관계 후보 + 관계 근거로 쓰일 대화 발췌/요약
- 비고/제약: 근거 표기가 부실하면 신뢰가 떨어지므로, 근거가 약한 관계는 표시하지 않거나 "현재 근거 충분치 않음"처럼 표기한다. ai-wiki 스킬의 갱신·연결 관습을 참고해 관계 후보를 생성한다.

**기능 F4 — 위키 읽기/탐색/검색**
- 설명: 정리된 위키를 주제별로 보고, 찾고 싶은 내용을 찾거나 관련 노드를 따라갈 수 있다.
- 사용자 스토리: "정리된 위키를 둘러보면서 예전에 했던 생각이나 아이디어를 다시 찾고 싶다."
- 우선순위: P0
- 입력: 사용자 탐색/검색 행동
- 출력/결과: 위키 뷰, 검색 결과, 관련 노드 제시
- 비고/제약: 비개발자도 쉽게 쓸 수 있게 명료하고 친근한 UI가 필요. 위키 노드 간 연결은 처음에 강제하지 않고 필요할 때 상호 참조 형태로 노출할 수 있다.

**기능 F5 — 제안 수락/기각/직접 편집 (사용자 통제)**
- 설명: 자동 제안을 사용자가 수락하거나, 기각하거나, 직접 수정할 수 있다. MVP 기준 **수락/기각**은 기본적으로 제공해야 하고, **직접 편집**은 후속 우선순위로 둔다.
- 사용자 스토리:
  - "제안받은 변경을 바로 적용하지 말고, 먼저 무엇이 바뀌는지 보고 수용/기각하고 싶다."
  - "적용한 결과가 새로고침해도 남아 있어야 하고, 내 결정과 변경 결과가 보존돼야 한다."
  - "자동 정리 결과가 마음에 안 들면 내가 직접 고칠 수 있으면 좋겠다."
- 우선순위: P0 (수락/기각 및 변경 전/후 미리보기, 결정 결과 보존) / P1 (직접 편집)
- 입력:
  - 사용자의 제안 수용/기각/수정 행동
  - 변경 전/후 비교에 필요한 위키 노드/내용 정보
- 출력/결과:
  - 제안별 수용/기각 상태와 적용 결과(위키 반영 여부, 변경 내용)
  - 결정 이력: 사용자가 어떤 제안을 언제 수용/기각했는지, 그 결과가 위키에 어떻게 남았는지 보존
  - 직접 수정이 일어난 경우 수정 내용과 반영 결과
- 비고/제약:
  - **수락 전에는 무엇을 바꿀지(변경 전/후)를 보여주어야 한다.** 결과만 던져서는 안 된다.
  - 수용/기각 결정과 그 적용 결과는 **새로고침/재접속 후에도 남아 있어야 한다.**
  - 직접 편집은 MVP 이후에 고도화 우선순위로 두되, 최소한 사용자가 결과를 통제할 수 있는 경로는 확보한다.
  - 제안 품질 개선을 위해 수용/기각 같은 피드백 신호를 이후 학습에 활용할 수 있어야 한다.
  - 스킬이 제안한 초안이 바로 위키로 확정되지 않도록 서비스 흐름에서 승인 단계를 거친다.

### 4.1.1 데이터 수신/저장/반영 흐름 (MVP)
 MVP에서의 데이터 전달과 위키 반영 흐름을 정의한다.

**(1) 전송 시작 방식 (MVP)**
- MVP에서는 **사용자가 명시적으로 "이 내용을 위키에 저장해줘"라고 요청**할 때 전송을 시작한다.
- 자동 스트리밍/주기 전송/대화 종료 자동 전송 등은 MVP 범위에서 제외한다.
- 전송은 **Solar 기반 에이전트 → 우리 서비스 MCP 도구 호출** 경로로 이뤄진다.
- 사용자는 에이전트와 대화 중 위키 저장 요청을 하고, 에이전트가 그 요청을 받아 MCP 도구로 전달한다.
- 호출 시 **대화 내용(구간 + 맥락)**이 우리 서비스로 전달된다.
※ ai-wiki-SKILL.md의 "호출 방식"(사용자용 프롬프트 세트, 3장)은 사용자가 직접 스킬을 호출할 때의 사용 방식이며, MVP 서비스 흐름에서는 Solar 에이전트 → MCP 도구 호출 경로를 통해 스킬이 간접적으로 실행된다. 즉, 스킬의 입력/처리/출력 구조는 동일하게 활용하되, 호출 주체와 경로가 다르다.

**(2) 전송 단위 (MVP)**
- MVP에서는 사용자가 **지정한 대화 구간**을 전송한다.
- 이때 대화 구간만 보내지 않고, **그 대화의 맥락(앞뒤 흐름, 어떤 주제/스킬/세션에서 나왔는지 여부 등)**을 함께 포함해서 보낸다.
- 즉, 단편 문장보다는 "구간에 속한 대화와 그 맥락"이 하나의 전송 단위가 된다.

**(3) 전달 후 보관 (MVP)**
- 전달받은 기록은 먼저 **보관**한다.
- 보관은 위키 반영과 분리해서 생각해야 하며, 나중에 정리/제안/검색에 쓸 수 있는 원본성 기록으로 남긴다.
- 보관은 두 층으로 생각할 수 있다.
  - 서비스 수신 원본: MCP 도구로 전달받은 대화 내용(구간 + 맥락) 자체를 보관하는 층
  - 사용자 추가 원본: 사용자가 직접 덧붙이거나 외부에서 가져온 원본
- 보관한 기록은 곧바로 위키로 바꾸기보다, **Solar + ai-wiki 스킬이 이를 읽어 위키 생성/변경 후보를 만드는 입력**으로 사용한다.
- MVP에서는 원본과 정리본이 섞이지 않게 관리하는 것이 중요하다.

**(4) 위키 생성/변경 제안 (MVP)**
- 우리 서비스는 전달받은 대화 내용(구간 + 맥락)을 바탕으로 **Solar + ai-wiki 스킬로 위키 생성/변경/추가/분리·연결 제안을 만든다.**
- 이때 ai-wiki 스킬은 서비스의 핵심 제안 생성기/초안 생성기로 동작하며, 서비스의 MCP 도구 호출을 통해 간접적으로 실행된다(사용자 직접 호출용 프롬프트와는 경로가 다르다). 스킬의 입력/처리/출력 구조는 그대로 활용하되, 서비스 흐름에서는 스킬이 생성한 초안과 변경 전·후를 **제안**으로 제시하고, 실제 위키 반영은 사용자의 수용/기각 결정 이후에만 이뤄진다.
- 이 구조 덕분에 스킬이 서비스에서 중심적인 역할을 하면서도, 스킬 출력이 곧바로 위키로 확정되지 않아 안정성을 확보할 수 있다.
- 제안은 결과만 던지지 않고, 적용 시 무엇이 바뀌는지(변경 전/후)를 함께 보여줘야 한다.

**(5) 사용자 확인 및 선택 반영 (MVP)**
- 사용자는 제안을 확인한 뒤, 변경 전/후를 보고 수용/기각 등 선택한다.
- 반영은 사용자 선택에 따라 이뤄지며, 결정과 결과는 새로고침/재접속 후에도 남아야 한다.
- 자동 제안이 곧바로 반영되는 구조가 아니라, **보관 → 후보 생성 → 제안 → 사용자 확인 → 사용자 선택 반영** 순서로 진행된다.

**(6) MVP에서 다루지 않는 것 (범위 제한)**
- 전체 대화를 항상 통째로 보내는 방식
- 자동 재전송/주기 동기화
- 사용자 요청 없이 대화 종료 시 자동 위키화
- 위와 같은 방식은 이후 고도화 검토 대상으로 남겨둔다.

우선순위가 낮은 기능 또는 2차 릴리즈 후보.
- 위키 노드 단위/타입 확장(예: 아이디어, 결정, 계획, 배움, 회고 등)
- 사용자 유형별 경험 세분화(개인 지식 정리, 팀 공유 등)
- 위키 공유/협업 기능
- 더 정교한 관계 그래프 시각화
- 사용자 피드백을 활용한 제안 품질 지속 개선

## 6. 사용자 경험 / UI 요구사항 (UX / UI Requirements)

### 6.1 주요 화면 / 플로우
 화면별 흐름을 기술하거나 와이어프레임/프로토타입 링크 첨부.
- 대화 입력/가져오기 화면: 사용자가 위키 저장을 요청하고 대화 구간 + 맥락을 전달하는 화면/흐름. MVP에서는 사용자가 명시적으로 위키 저장을 요청하는 방식이 중심이며, 필요하면 이후 가져오기 방식도 확장 가능
- 위키 허브(주제별 노드 목록): 정리된 위키를 주제별로 보고 탐색하는 화면
- 개별 위키 노드(내용 + 관련 제안 + 관계 제안): 노드 내용과 함께 관련 제안, 과거-최근 관계 제안을 보는 화면
- 제안 수용/기각/수정 인터페이스: 변경 전/후 미리보기와 함께 제안을 확인하고 수용/기각/수정하는 화면
- 처음 사용 흐름/온보딩 힌트: 위키가 아직 없거나 적을 때는 "아직 연결할 위키가 많지 않아요. 먼저 대화 구간을 위키에 저장해 보세요" 같은 안내로 시작. 폴더·태그·위키 구조를 미리 설계하지 않아도 시작할 수 있도록, 처음에는 제안된 구조와 노드를 그대로 따라가며 익숙해지도록 안내

### 6.2 디자인 원칙
- **낮은 진입장벽**: 개발자뿐 아니라 AI를 쓰는 일반 사용자도 처음 보고 이해할 수 있어야 함.
- **명료성**: 추가/변경·분리·연결 같은 개념도 너무 무겁지 않게, 짧고 직관적으로 표현.
- **통제감**: 자동 정리가 기본이지만 사용자가 수락/기각/직접 편집할 수 있어야 함.
- **자동과 승인의 분리**: 대화 읽기, 위키 후보/제안 후보 생성은 자동화 구간이고, 실제 위키에 반영(추가/변경·분리·연결 등)은 사용자 승인 구간에서 이뤄지도록 설계한다. 자동 제안이 곧바로 반영되는 구조가 아니라, 승인 전후로 변경 전/후를 확인하고 결정하게 한다.
- **근거 투명성**: 관계/제안을 제시할 때 왜 그런지 근거를 함께 보여줘야 신뢰를 얻음.
- **과도한 자동화 회피**: 초반에는 신뢰 높은 제안만 보수적으로 보여주고, 사용자에게 피로가 쌓이지 않게 함.
- **구조 부담 완화**: 폴더·태그·위키 구조를 미리 설계하지 않아도 시작할 수 있어야 하며, 필요하면 기본 구조를 제안할 수 있되 임의로 확정하지 않음. 모호한 항목은 모호하게 남김.

### 6.3 에러 / 예외 처리
 주요 에러 케이스와 사용자에게 보여줄 안내 방식.
- 대화/스킬 데이터를 읽지 못할 때
- 위키 구조가 아직 비어 있거나 너무 적을 때
- 제안의 근거가 약해서 표시하지 않는 경우의 처리 방식(묵살 or "현재 근거 충분치 않음" 표기)
- 스킬 호출/처리 실패 시: 제안 생성을 재시도하거나, 실패 원인을 안내하고 위키 반영을 보류. 실패해도 기존 위키가 손상되지 않도록 함
- 저장소/반영 실패 시: 반영 실패를 안내하고, 사용자 결정과 반영 결과를 가능한 범위에서 보존해 재시도 가능하게 함

## 7. 데이터 모델 / API (Data Model & API)

### 7.1 핵심 엔티티
 주요 엔티티와 관계 요약 (ERD 스케치 또는 링크).
- 사용자
- 대화/스킬 출처(대화 묶음, 세션 등)
- 위키 노드(주제/엔티티 단위)
- 위키 노드 내용(요약, 발췌, 메타데이터)
- 관계/제안(추가, 변경·분리·연결, 관계 제시 등)
- 제안 상태/승인 이력(제안 후보, 변경 전/후 미리보기, 수용/기각, 반영 결과, 결정 시점)
- 사용자 피드백(수용/기각/수정 등)

※ 제안 후보는 "생성됨"과 "승인/기각/반영됨" 상태를 구분해 관리해야 한다.
자동으로 만든 후보와 실제 위 키에 반영된 결과를 혼동하지 않도록, 제안→승인→반영 흐름을 별도 상태/이력으로 추적한다.

### 7.1.1 위키 저장 구조 (MVP)
 전달받은 대화가 어떤 위키로 저장되는지 정의한다.

**(1) 원본 보관과 위키 정리본 분리 (MVP)**
- 전달받은 대화/맥락 기록은 먼저 **원본 보관 영역**에 남긴다.
- 위키 정리본은 원본과 분리된 영역에 저장한다.
- 원본은 입력 당시의 기록을 보존하는 용도이고, 위키 정리본은 꺼내 읽기 좋게 재구성한 결과물이다.
- MVP에서는 원본과 정리본이 섞이지 않게 관리하는 것이 중요하다.
- 서비스 수신 원본과 사용자 추가 원본을 구분해 보관할 수 있다.

**(2) 위키 노드 저장 방식 (MVP)**
- 위키는 **주제/엔티티 단위의 노드**로 저장한다.
- 각 노드는 제목, 한 줄 요약, 핵심 내용, 관련 아이디어/링크/연결 후보 같은 기본 항목을 가진다.
- 새 대화 구간은 대화 전체를 무조건 하나의 노드로 만드는 방식이 아니라, 내용 성격에 따라 위키 노드로 정리한다.
- 같은 주제가 이미 있으면 별도 노드를 무작정 만들지 않고, 기존 노드에 병합할지/분리할지/연결만 유지할지 제안한다.
- MVP에서는 위키 노드가 곧 위키 정리본 영역의 개별 마크다운 파일/주제 단위 항목과 대응될 수 있으며, 주제 디렉터리 구조는 노드를 그룹핑하는 분류로 사용 가능하다.
- 노드 간 연결은 처음에 강제하지 않고 필요할 때 상호 참조 형태로 노출할 수 있다.

**(3) 대화 구간 → 위키 노드 매핑 (MVP)**
- 사용자가 지정한 대화 구간은 **맥락과 함께** 전달되므로, 위키 노드는 "단편 문장"이 아니라 "맥락이 있는 내용 단위"를 반영한다.
- 하나의 대화 구간이 여러 위키 노드에 걸쳐 관련될 수 있고, 반대로 한 위키 노드가 여러 대화 구간에서 보강될 수 있다.
- 이 관계를 추적 가능하게 남겨야, 나중에 어떤 대화에서 어떤 위키 노드가 보강됐는지 확인할 수 있다.

**(4) 갱신/누적 방식 (MVP)**
- 같은 위키 노드를 다시 만날 때는 무조건 새로 만들지 않는다.
- 새 내용이 들어오면 기존 내용을 가능한 한 보존하면서 갱신/보완을 추가한다.
- 필요하면 갱신 기록(언제, 어떤 변경이 있었는지)을 남긴다.
- 방향이 다른 내용은 새 노드로 분리할 수 있고, 그 판단은 병합/분리 제안으로 남긴다.
- 갱신 기록은 노드 파일 내부 또는 별도 이력/메타 방식으로 관리 가능하다.

**(5) 위키 저장 시 명시할 것 (MVP)**
- 어떤 원본 대화 구간이 어떤 위키 노드에 반영됐는지
- 어떤 변경이 있었는지(변경 전/후)
- 제안이 수용됐는지/기각됐는지
- 위키가 자동 반영된 것이 아니라 사용자 선택에 따라 반영됐는지
- 추가로 제안 상태(생성됨/승인/기각/반영됨), 결정 시점, 반영 결과, 거절 후 재제안 여부 등도 추적 가능하다.

※ 세부 스키마와 저장 형식은 MVP 설계 단계에서 확정한다.

- 위키 저장 요청 → 보관 → 스킬 제안 생성 → 변경 전/후 표시 → 수락/기각/결과 보존 흐름이 정상 동작하고,
- 위키가 비어 있거나 제안이 없을 때도 무너지지 않으며,
- 실패 시에도 기존 데이터가 손상되지 않는 수준

## 9. 리스크 & 의존성 (Risks & Dependencies)

| 리스크 | 설명 | 완화 방안 |
|---|---|---|
| 제안 품질이 낮으면 스팸처럼 느껴질 수 있음 | 근거 부실/과도한 제안은 신뢰를 떨어뜨림 | 초반 보수적 제안, 근거 표기, 사용자 피드백 반영 |

| 대화가 너무 적으면 위키/제안이 빈약할 수 있음 | 초기 데이터 부족 시 가치 체감이 어려움 | 비어 있는 상태 UX 고려, 점진적 적립 경험 설계 |
| 비개발자 사용자에게 개념이 어렵게 느껴질 수 있음 | 추가/변경·분리·연결 같은 표현이 부담될 수 있음 | 친근한 표현, 짧은 설명, 점진적 노출 |
| 스킬 호출/처리 실패 또는 제안 생성 불안정 | LLM 출력 편차, 처리 지연, 실패 시 서비스 중단 우려 | 재시도/대체 안내, 실패 시 기존 위키 보호, 비동기/백그라운드 처리 검토, 제안 품질 하한선/보수적 노출 |
| 원본/정리본 혼합 또는 반영 결과 혼선 | 서비스 수신 원본과 정리본이 섞이거나 제안 상태가 실제 반영 결과와 혼동될 수 있음 | 원본 보관 영역과 위키 정리본 분리, 제안 상태/승인 이력/반영 결과 별도 추적, 사용자 선택 반영만 실제 반영 |

외부 의존성: 대화/스킬 데이터 접근 방식, 위키 UI/프런트엔드, 필요 시 외부 분석 도구 등.

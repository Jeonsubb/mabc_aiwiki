아키텍처

01개요

1.1 제품 설명

사용자가 AI와 주고받은 대화를 읽고, 개인화된 주제별 위키로 정리해 제공하는 웹 서비스입니다.

에이전트가 생성한 결과는 위키에 바로 쓰지 않고 제안 형태로만 제시하며, 사용자가 수락한 내용만 실제 개인 위키에 반영됩니다. 즉, 자동 정리 및 그래프 구축과 사람의 통제(수락/기각)를 함께 제공합니다.

개발자뿐 아니라 AI를 사용하는 모든 사용자를 대상으로 하며, 기술 지식뿐 아니라 아이디어·결정·계획·배움·회고 등 일상적 대화도 위키 형태로 다룰 수 있어야 합니다.

자동과 승인의 구분
여기서 말하는 자동 제안 및 자동 정리란 대화를 읽어 위키 노드·제안 후보를 만드는 구간까지를 뜻합니다. 후보를 실제 위키에 반영하는 단계는 반드시 사용자 승인을 거칩니다. 즉 후보 생성은 자동화 영역, 실제 반영은 사용자 승인 영역입니다.

1.2 목표

  • 개발자뿐 아니라 AI를 사용하는 일반 사용자도 부담 없이 쓸 수 있는 낮은 진입장벽과 친근한 경험을 제공합니다.
  • 외부 AI 대화를 MCP를 통해 사용자별로 안전하게 수신하고 보관합니다.
  • Solar Pro 4가 ai-wiki 스킬로 대화를 읽어 신규 위키 생성, 기존 위키 갱신, 위키 간 연결을 제안합니다.
  • 사용자가 변경 내용과 원문 근거를 확인한 뒤 제안을 수락하거나 기각할 수 있도록 합니다.
  • 수락된 결과만 개인 위키와 생각 지도에 반영합니다.
  • 같은 주제의 후속 대화가 기존 위키의 갱신 제안으로 이어지도록 합니다.
  • Solar가 AutoSchema의 스키마 유도 방식을 참고해 노드의 개념적 역할과 관계 유형을 판단하도록 합니다.

1.3 범위

포함제외
AI와 주고받은 대화를 주제별 위키로 정리단순 채팅 로그 보관만 하고 구조화하지 않는 방식
새 대화 유입 시 기존 위키 대조 후 신규·갱신·연결 제안 (초반 보수적 제안 + 근거 제시)근거 없이 연관성만 나열하는 추천 스팸성 기능
과거 아이디어와 최근 맥락 사이 유용한 관계를 근거와 함께 제시근거 표기 없는 자동 연관성 엔진
개발자뿐 아니라 일반 사용자도 쓸 수 있는 친근한 인터페이스와 낮은 진입장벽특정 개발 도구/언어 전용 지식베이스로 한정
MCP를 통한 사용자 요청 기반 대화 원문 수신·보관사용자 요청 없이 대화를 자동 수집하는 기능
Solar Pro 4가 ai-wiki 스킬로 만드는 신규·갱신·연결 제안AI가 생성한 내용을 사용자 승인 없이 바로 위키에 반영하는 기능
변경 전후와 원문 근거를 확인한 뒤 수락·기각제안 내용을 사용자가 직접 편집하는 기능
AutoSchema의 스키마 유도 방식을 참고한 관계 유형 추론AutoSchemaKG 전체 파이프라인 및 자동 스키마 데이터베이스 구축
사용자가 승인한 위키 관계를 생각 지도에 표시승인되지 않은 관계를 자동 확정하는 기능
위키와 보관 대화에 대한 기본 키워드 검색개인화 랭킹·벡터 검색·그래프 경로 검색
TBD: 추후 사용자 유형별 확장(개인 지식 정리, 팀 공유 등)지금 단계에서 확정할 세부 사용자 유형 분류

02문제 정의

2.1 배경

  • AI를 자주 쓰는 사람들은 대화 내용이 쌓이지만, 나중에 다시 찾아보기 어렵습니다.
  • 기록 자체가 흩어져 있으면, 예전 아이디어가 지금 맥락과 연결되는 지점을 놓치기 쉽습니다.
  • 위키로 정리하면 꺼내 쓰기 좋지만, 사람이 매번 정리하기엔 부담이 큽니다.

2.2 해결할 문제

문제 1

기록으로만 남는 대화

AI와 주고받은 대화가 기록으로만 남고, 주제별 지식으로 다시 꺼내 쓰기 어렵습니다.

문제 2

연결되지 않는 새 대화

새 대화가 들어와도 기존 기록과 연결되지 않아, 과거 아이디어와의 관계가 표면화되지 않습니다.

문제 3

높은 진입장벽

개발자 중심으로만 설계된 도구는 비개발자가 쓰기엔 진입장벽이 높습니다.

2.3 기대 효과

  • 사용자가 따로 정리하지 않아도 대화 기록이 위키 형태로 남아 재탐색 비용이 낮아집니다.
  • 새 대화 유입 시 기존 위키와의 관계가 제안되어, 위키가 정적 저장소가 아니라 진화하는 지식 기반이 됩니다.
  • 과거와 현재 맥락 사이의 관계가 근거와 함께 제시되어, 예전 아이디어를 지금 상황에서 다시 활용할 가능성이 높아집니다.
  • 비개발자도 쓸 수 있는 경험을 제공함으로써, AI를 사용하는 더 넓은 사용자층에게 가치를 전달할 수 있습니다.
  • 대화가 일회성 채팅으로 끝나지 않고 신규 위키 또는 기존 위키의 갱신안으로 누적됩니다.
  • 사용자는 제안의 변경 내용과 원문 근거를 확인한 후 수락 여부를 결정할 수 있습니다.
  • 기존 위키 사이의 관계가 근거와 함께 제안되어, 따로 보관된 생각을 연결해서 볼 수 있습니다.
  • 승인된 관계가 생각 지도에 표시되어 사용자가 자신의 지식 구조를 시각적으로 탐색할 수 있습니다.

F1: 대화 읽어서 위키 노드 만들기

P0

MCP로 전달된 대화 원문을 Solar Pro 4가 ai-wiki 스킬로 분석해 주제별 위키 노드 후보를 만듭니다. 기존 위키와 같은 주제라면 신규 노드보다 기존 위키 갱신을 우선합니다.

"AI와 나눈 대화 기록을 선택하면, 주제별로 정리된 위키 노드가 자동으로 만들어지면 좋겠다."

입력

  • MCP를 통해 전달된 대화 원문
  • 기존 위키 노드

출력 / 결과

  • 제목, 요약, 본문, 주제, 태그, 분류를 포함한 신규 위키 후보
  • 또는 기존 위키 갱신 제안

제약: 생성 결과는 위키에 바로 반영하지 않고 제안 상태로 저장합니다.

F2: 제안 수락/기각

P0

사용자는 자동 생성된 제안의 내용과 근거를 검토한 뒤 수락하거나 기각할 수 있습니다.

출력 / 결과

  • 수락된 신규 제안은 위키 노드로 저장
  • 수락된 갱신 제안은 기존 위키와 버전 이력에 반영
  • 수락된 연결 제안은 위키 관계로 저장

 

  • 기각된 제안은 위키에 반영하지 않음
  • 결정 상태와 시각은 새로고침 후에도 유지

제약: 사용자가 제안 내용을 직접 편집하는 기능은 MVP 범위에 포함하지 않습니다.

F3: 새 대화 유입 시 기존 위키 대조 후 제안

P0

새로운 대화가 들어오면 기존 위키를 검토해, 신규 생성·갱신·연결이 필요해 보이는 내용을 사용자에게 제안합니다.

"새로운 대화를 넣으면 기존 위키를 보고 '이 내용을 여기에 붙이면 좋겠다' 같은 제안을 해주면 좋겠다."

입력

  • 새로 들어온 대화
  • 기존 위키 노드

출력 / 결과

  • 신규 위키 생성 제안
  • 기존 위키 갱신 제안
  • 기존 위키 간 연결 제안
  • 제안 이유와 원문 근거
  • 갱신 제안의 변경 전후 미리보기

비고 / 제약

  • 초반에는 가장 신뢰도 높은 제안만 보수적으로 보여줍니다.
  • 제안은 결과만 던지는 게 아니라, 사용자가 수락하기 전에 무엇이 바뀌는지 알 수 있어야 합니다.
  • 사용자가 수락/기각할 수 있어야 하며, 그 결정과 결과는 다음 새로고침/재접속 후에도 남아 있어야 합니다.

F4: 위키와 보관 대화 검색

P1

사용자는 키워드로 승인된 위키와 서비스에 보관된 대화를 함께 검색할 수 있습니다.

"예전에 저장한 위키나 대화 내용을 키워드로 다시 찾고 싶다."

입력

  • 사용자의 검색어

출력 / 결과

  • 검색어가 포함된 위키 노드
  • 검색어가 포함된 보관 대화
  • 검색 결과에서 위키 상세 또는 원본 대화로 이동

제약: 개인화 랭킹, 벡터 검색, 그래프 경로 검색은 현재 MVP 범위에 포함하지 않습니다.

F5: Solar 기반 동적 관계 스키마 유도 및 연결 제안

P0

Solar Pro 4는 AutoSchema의 데이터 기반 스키마 유도 방식을 참고해, 기존 위키 노드와 새 대화에서 노드의 개념적 역할과 관계 유형을 추론합니다. 이를 바탕으로 근거가 있는 위키 연결 후보를 생성합니다.

"서로 관련된 위키가 있다면 어떤 관계인지와 왜 연결되는지 확인하고 직접 승인하고 싶다."

입력

  • 새 대화 원문
  • 기존 위키 노드
  • 원문 세그먼트

출력 / 결과

  • 출발 위키와 도착 위키
  • 각 위키의 개념적 역할
  • 관계 유형
  • 관계 판단 이유
  • 원문 근거

제약

  • 공통 단어 또는 태그가 있다는 이유만으로 연결하지 않습니다.
  • 관계의 의미와 원문 근거가 명확하지 않으면 제안하지 않습니다.
  • 관계 후보는 제안 목록에만 저장하며 사용자 승인 전에는 확정하지 않습니다.
  • 사용자가 수락한 관계만 생각 지도에 표시합니다.

구현 범위: AutoSchemaKG 전체 라이브러리를 실행하는 것이 아니라, 데이터에서 개념 유형과 관계 유형을 유도한 뒤 관계를 추출하는 핵심 방식을 Solar의 구조화 출력에 적용합니다.

04-1데이터 수신 · 저장 · 반영 흐름

MVP에서의 데이터 전달과 위키 반영 흐름을 정의합니다. 자동 제안이 곧바로 반영되는 구조가 아니라 보관 → 후보 생성 → 제안 → 사용자 확인 → 사용자 선택 반영 순서로 진행됩니다.

1

전송 시작

사용자의 명시적 저장 요청 → 에이전트가 MCP 도구 submit_conversation 호출

2

보관

원문 구간 + 맥락을 원본 보관 영역에 저장. 정리본과 분리

3

후보 생성

Solar Pro 4가 ai-wiki 스킬로 기존 위키와 대조해 신규·갱신·연결 제안 생성

4

사용자 확인

변경 전후와 원문 근거를 보고 수락 / 기각

5

반영

수락한 것만 위키·버전 이력·관계·생각 지도에 반영

(1) 전송 시작 방식

  • MVP에서는 사용자가 명시적으로 "이 내용을 위키에 저장해줘"라고 요청할 때만 전송을 시작합니다. 자동 스트리밍, 주기 전송, 대화 종료 자동 전송은 제외합니다.
  • 전송은 Solar 기반 에이전트 → 우리 서비스 MCP 도구 호출 경로로 이뤄지며, 대화 내용(구간 + 맥락)이 전달됩니다.
  • 저장 요청의 해석: "위키에 저장해"처럼 말하면 저장 요청으로 해석하고 별도 확인 없이 submit_conversation을 호출합니다.
  • 구간 지정 우선: 사용자가 특정 구간을 지정했으면 그 구간만 보냅니다. 지정하지 않았고 현재 주제가 진행 중이면, 위키에 남길 가치가 있는 내용(주제·아이디어·결정·계획·배움·회고)이 포함된 하나의 주제 범위로 묶어 보냅니다.
  • 질문은 불명확할 때만: 어떤 구간·주제인지 에이전트도 판단할 수 없을 때만 범위를 확인하는 질문을 합니다.
  • 보이는 대화만 전송: 에이전트에게 실제로 보이는 내용만 보내며, 없는 대화를 추론해 만들어내지 않습니다.
  • 저장 요청 없으면 전송하지 않음: 대화가 끝났어도 자동으로 전송하지 않습니다.
  • 에이전트 지침에서 저장 요청 처리의 연결 위치를 찾을 수 없으면 임의로 행동하지 않고 누락 사실을 보고합니다.

(2) 전송 단위 및 입력 계약

submit_conversation은 역할 구분 메시지 목록(messages) 또는 대화 텍스트(conversation_text) 중 하나로 원문 구간을 전달합니다. 둘이 함께 오면 불일치 검사를 수행합니다.

필드필수설명
session_id필수대화/세션을 식별하는 ID
conversation_text선택전송할 대화 원문(구간). messages가 없을 때 사용
messages[]선택역할이 구분된 메시지 목록. 각 항목은 role, content 필수, record_id, timestamp(ISO 8601) 선택. 제공되면 원문의 1차 출처
source선택전송 출처 구분. 예: mcp, agent, user_direct
context선택주제, 스킬, 세션 유형, 앞뒤 흐름 등 보충 맥락. 대화 원문 자체는 넣지 않는다

입력 계약 원칙

  • role과 content 중 하나라도 누락되면 도구 오류로 처리합니다. 알 수 없는 id나 시각을 추측해 넣지 않습니다.
  • messages와 conversation_text가 함께 오면, 메시지를 역할과 함께 연결한 재구성 텍스트와 conversation_text를 공백·개행 정규화 후 비교합니다. 실질적으로 같으면 정상 처리하고, 다르면 도구 오류로 처리합니다.
  • 기존 conversation_text 기반 호출은 계속 지원합니다.

예시 (messages 방식)

{
  "session_id": "sess-12345",
  "source": "agent",
  "messages": [
    { "role": "user", "content": "동네 산책 사진으로 사진집을 만들까 고민 중이야.", "record_id": "msg-001", "timestamp": "2026-09-15T10:00:00+09:00" },
    { "role": "assistant", "content": "사진집은 인쇄와 전자책 두 가지 형식이 있어요. 어떤 쪽으로 생각하세요?", "record_id": "msg-002", "timestamp": "2026-09-15T10:00:15+09:00" },
    { "role": "user", "content": "아직 정리는 안 됐고, 일단 아이디어만 보관해두고 싶어.", "record_id": "msg-003", "timestamp": "2026-09-15T10:00:30+09:00" }
  ],
  "context": { "topic": "사진집 기획", "skill": "ai-wiki" }
}

(3) 전달 후 보관

  • 전달받은 기록은 먼저 보관합니다. 보관은 위키 반영과 분리하며, 나중에 정리·제안·검색에 쓸 원본성 기록으로 남깁니다.
  • 보관은 두 층입니다. 서비스 수신 원본(MCP로 전달받은 구간 + 맥락)과 사용자 추가 원본(사용자가 직접 덧붙이거나 외부에서 가져온 원본).
  • 보관한 기록은 곧바로 위키로 바꾸지 않고, Solar Pro 4가 ai-wiki 스킬로 읽어 위키 생성/변경 후보를 만드는 입력으로 씁니다.

(4) 위키 생성/변경 제안 · (5) 사용자 확인 및 선택 반영

  • 전달받은 대화 내용을 바탕으로 Solar Pro 4가 ai-wiki 스킬로 신규·갱신·연결 제안을 만들고, 적용 시 무엇이 바뀌는지(변경 전/후)를 함께 보여줍니다.
  • 사용자는 제안을 확인한 뒤 변경 전/후를 보고 수락 또는 기각합니다. 결정과 결과는 새로고침·재접속 후에도 남습니다.

(6) MVP에서 다루지 않는 것

  • 전체 대화를 항상 통째로 보내는 방식, 자동 재전송/주기 동기화, 사용자 요청 없이 대화 종료 시 자동 위키화
  • 2차 릴리즈 후보: 위키 노드 타입 확장(아이디어·결정·계획·배움·회고), 사용자 유형별 경험 세분화, 위키 공유/협업, 더 정교한 관계 그래프 시각화, 사용자 피드백을 활용한 제안 품질 지속 개선

06사용자 경험 / UI 요구사항

6.1 주요 화면 / 플로우

화면 1

생각 지도 (홈)

승인된 위키 노드와 관계를 그래프로 탐색합니다. 노드를 선택하면 요약과 정리 본문, 전체 보기, 대화로 이어가기를 제공합니다.

화면 2

내 위키 · 위키 상세

주제별 노드 목록과 개별 노드의 제목·요약·본문·주제 태그·갱신 이력.

화면 3

제안 목록 · 제안 상세

신규·갱신·연결 제안을 유형·상태 배지와 함께 나열하고, 상세에서 변경 전후 비교와 원문 근거를 확인한 뒤 수락 또는 기각합니다.

화면 4

유입 기록 · MCP 연결 · 검색

보관된 대화 원문 목록, 에이전트 연동용 토큰 발급 화면, 위키와 보관 대화를 함께 찾는 검색 결과.

6.2 디자인 원칙

  • 낮은 진입장벽: 개발자뿐 아니라 AI를 쓰는 일반 사용자도 처음 보고 이해할 수 있어야 합니다.
  • 명료성: 신규/갱신/연결 같은 개념도 무겁지 않게, 짧고 직관적으로 표현합니다.
  • 통제감: 자동 정리가 기본이지만 반영 여부는 항상 사용자가 수락/기각으로 결정합니다.
  • 자동과 승인의 분리: 대화 읽기와 후보 생성은 자동화 구간, 실제 위키 반영은 승인 구간입니다. 승인 전에 변경 전/후를 확인하고 결정하게 합니다.
  • 근거 투명성: 관계/제안을 제시할 때 왜 그런지 근거를 함께 보여줍니다.
  • 과도한 자동화 회피: 초반에는 신뢰 높은 제안만 보수적으로 보여주고 사용자에게 피로가 쌓이지 않게 합니다.

6.3 에러 / 예외 처리

  • 대화/스킬 데이터를 읽지 못할 때: 유입 기록에 실패 상태와 사유를 남기고 사용자에게 안내합니다.
  • 위키 구조가 아직 비어 있거나 너무 적을 때: 빈 상태 화면에서 다음 행동(대화 저장, 제안 확인)을 안내합니다.
  • 제안의 근거가 약해서 표시하지 않는 경우: 제안을 만들지 않거나 "현재 근거 충분치 않음"으로 표기합니다.

07데이터 모델 / API

7.1 핵심 엔티티

엔티티역할
사용자 (User)모든 데이터의 격리 단위. MCP 연결 토큰의 소유자
유입 기록 (Record)MCP 또는 직접 입력으로 들어온 대화 원문과 맥락. 원본 보관 영역
대화 세그먼트 (ConversationSegment)원문을 근거 단위로 나눈 조각. 제안의 근거(evidence)가 가리키는 대상
위키 노드 (WikiNode) · 노드 버전 (NodeVersion)주제/엔티티 단위 정리본과 갱신 이력
제안 (Proposal) · 제안 근거 (ProposalEvidence)신규·갱신·연결 후보, 변경 전/후, 상태(제안됨·승인됨·기각됨·반영됨), 결정 시각, 원문 인용
노드 관계 (NodeRelationship)수락된 연결 제안에서 생긴 관계. 관계 유형과 근거를 가지며 생각 지도에 표시
원본→노드 매핑 (RecordToNode)어떤 원문 구간이 어떤 노드에 반영됐는지 추적
MCP 연결 토큰 (McpCredential)에이전트가 사용자 계정으로 대화를 제출할 때 쓰는 Bearer 토큰
제안 후보는 "생성됨"과 "승인/기각/반영됨" 상태를 구분해 관리합니다. 자동으로 만든 후보와 실제 위키에 반영된 결과를 혼동하지 않도록 제안→승인→반영 흐름을 별도 상태·이력으로 추적합니다.

7.1.1 위키 저장 구조

원본 보관 영역

  • MCP로 전달받은 대화 구간 + 맥락
  • 사용자가 직접 덧붙인 원본
  • 입력 당시의 기록을 그대로 보존
  • 세그먼트 단위로 근거 참조 가능
→

위키 정리본 영역

  • 주제/엔티티 단위 노드(제목·요약·본문·주제·태그·분류)
  • 수락된 갱신은 기존 내용을 보존하며 새 버전으로 누적
  • 수락된 연결은 관계로 저장되어 생각 지도에 표시
  • 어떤 원문이 어떤 노드에 반영됐는지 매핑
  • 분리 원칙: 원본과 정리본이 섞이지 않게 관리합니다. 원본은 보존 용도, 정리본은 꺼내 읽기 좋게 재구성한 결과물입니다.
  • 매핑: 하나의 대화 구간이 여러 노드에 걸칠 수 있고, 한 노드가 여러 구간에서 보강될 수 있습니다. 이 관계를 추적 가능하게 남깁니다.
  • 갱신/누적: 같은 주제를 다시 만나면 새로 만들지 않고 기존 내용을 보존하며 갱신하고, 언제 어떤 변경이 있었는지 버전 이력을 남깁니다.
  • 저장 시 명시할 것: 어떤 원본 구간이 어떤 노드에 반영됐는지, 어떤 변경이 있었는지(전/후), 제안이 수락됐는지 기각됐는지, 자동 반영이 아니라 사용자 선택으로 반영됐는지.

08성공 지표

8.1 MVP 성공 기준

  • MCP로 제출한 대화가 사용자 계정의 유입 기록에 저장됩니다.
  • 제출된 대화에서 최소 한 개 이상의 신규·갱신·연결 제안을 생성할 수 있습니다.
  • 신규 제안을 수락하면 내 위키에 노드가 생성됩니다.
  • 같은 주제의 후속 대화가 기존 위키 갱신 제안으로 이어집니다.
  • 연결 제안을 수락하면 생각 지도에 두 위키의 관계선이 표시됩니다.
  • 기각한 제안은 위키에 반영되지 않습니다.
  • 새로고침 후에도 위키와 결정 상태가 유지됩니다.

8.2 추적 방법

  • 위키 열람, 노드 클릭, 제안 노출/수락/기각, 관계 제시 노출/클릭 등 이벤트 설계
  • 초기엔 과도한 이벤트보다 핵심 행동 위주로 추적

09리스크 & 의존성

리스크설명완화 방안
제안 품질이 낮으면 스팸처럼 느껴질 수 있음근거 부실/과도한 제안은 신뢰를 떨어뜨림초반 보수적 제안, 근거 표기, 사용자 피드백 반영
자동 정리가 사용자의 통제감을 약화시킬 수 있음위키가 사용자 의도와 다르게 정리될 수 있음모든 반영을 수락/기각 승인 뒤에만 수행
대화가 너무 적으면 위키/제안이 빈약할 수 있음초기 데이터 부족 시 가치 체감이 어려움비어 있는 상태 UX 고려, 점진적 적립 경험 설계
비개발자 사용자에게 개념이 어렵게 느껴질 수 있음신규/갱신/연결 같은 표현이 부담될 수 있음친근한 표현, 짧은 설명, 점진적 노출

외부 의존성: Solar Pro 4 API(Upstage), MCP 클라이언트를 가진 에이전트(Hermes 등), PostgreSQL, 프론트/백엔드 호스팅.
